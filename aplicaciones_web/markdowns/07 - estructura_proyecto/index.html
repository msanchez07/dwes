    Organizando el código

    Hasta este punto, la creación de aplicaciones PHP se ha centrado en el uso de scripts separados, donde cada archivo se encarga de una tarea concreta o representa una página específica dentro del sitio web. Este enfoque es directo y funcional para proyectos de pequeña escala. Sin embargo, en el momento en que la aplicación crece y la complejidad aumenta, esta estructura lineal se vuelve insostenible. El código comienza a volverse un amasijo de responsabilidades mezcladas, donde la lógica de la aplicación se encuentra entremezclada con consultas a la base de datos y etiquetas HTML. El resultado es un código difícil de leer, propenso a errores y extremadamente complicado de mantener o escalar, ya que un cambio en una parte puede afectar inesperadamente a otras.

    Para superar este desafío, es imperativo adoptar una arquitectura de aplicación sólida y patrones de diseño establecidos. La piedra angular de esta modernización es la implementación del patrón Modelo-Vista-Controlador (MVC), el cual promueve la separación de responsabilidades. En lugar de que un único script lo haga todo, nuestro código se divide en tres componentes especializados: los Modelos que gestionan los datos, las Vistas que manejan la presentación visual, y los Controladores que actúan como intermediarios para procesar la lógica de negocio. Esta estructura organizada, complementada por el Enrutador, garantiza que cada parte del código tenga un propósito claro y un lugar definido, haciendo que nuestra aplicación sea robusta, predecible y capaz de crecer de manera profesional.

    Para aplicar correctamente la separación de responsabilidades que impone el patrón MVC, nuestro proyecto se organiza en directorios específicos, cada uno con un propósito bien definido. La estructura se divide principalmente en tres secciones: la capa de Aplicación (app/), que contiene la lógica de negocio y la presentación; el Núcleo (core/), que alberga la funcionalidad esencial del framework como el Enrutador y el Contenedor de Servicios; y el punto de acceso público (public/), que actúa como la única puerta de entrada. Esta organización aísla los archivos internos del acceso directo del usuario, aumentando la seguridad y la claridad del sistema, al mismo tiempo que establece un lugar claro para cada tipo de código que desarrollemos.

    /
├── app/
│   ├── controller/  # Los Controladores que gestionan las peticiones
│   ├── models/      # Los Modelos para interactuar con la base de datos
│   ├── services/    # Servicios como la conexión a la BD
│   └── views/       # Las Vistas, que contienen el código HTML
├── core/
│   ├── Container.php # Contenedor de servicios para dependencias
│   ├── Controller.php# La clase base de la que heredan los Controladores
│   └── Router.php    # La clase principal que maneja las URLs
├── database/
│   └── database.sqlite # Archivo de base de datos
├── public/
│   ├── index.php     # El punto de entrada único (Front Controller)
│   └── css/          # Archivos estáticos como CSS
├── routes.php        # El archivo donde se definen las rutas de la aplicación
└── README.md

    En las siguientes secciones vamos a ir explicando poco a poco esta estructura y las distintas clases que lo componen.

    El Corazón del Arranque: index.php

    El archivo public/index.php no es una simple página web, sino el Front Controller de nuestra aplicación, el portero que centraliza y dirige todo el tráfico. Para el desarrollador experto, este archivo es el bootstrap o motor de arranque, donde se realiza el ritual cuidadosamente orquestado de la inicialización antes de que la lógica de negocio entre en juego.

    Este proceso comienza con la necesidad de establecer un sistema de coordenadas inmutable, ya que trabajar con rutas relativas en PHP es una fuente constante de errores; por ello, definimos constantes de ruta absolutas utilizando el truco del oficio: dirname(__DIR__), que sube un nivel desde el directorio public para establecer BASE_PATH como la raíz de nuestro proyecto, a partir de la cual se define el camino hacia las Vistas en VIEWS_PATH, como se muestra a continuación:

    <?php
        // BASE_PATH: La raíz del proyecto.
    define('BASE_PATH', dirname(__DIR__));

    // VIEWS_PATH: Ruta a la carpeta de vistas.
    define('VIEWS_PATH', BASE_PATH . '/app/views');

    Aquí, dirname(__DIR__) es el truco del oficio: le dice al sistema que suba un nivel desde el directorio public, estableciendo un punto de referencia (BASE_PATH) a la raíz de nuestra aplicación que es independiente de la URL que el usuario haya tecleado. Sobre esta base, se define el camino hacia los archivos de presentación, o Vistas, encapsulados en VIEWS_PATH.

    Tras establecer las rutas, abordamos la gestión manual de dependencias, una práctica obsoleta que se soluciona implementando la carga automática de clases mediante el estándar PSR-4, lo cual hace que nuestro código parezca y funcione como un framework profesional.

    La función spl_autoload_register es nuestra aliada, registrando una función anónima que interviene solo cuando PHP necesita una clase desconocida. La lógica interna de esta función se basa en la convención: un mapa predefine que el namespace App\ se corresponde con el directorio /app/ y Core\ con /core/. Al solicitar, por ejemplo, App\controller\HomeController, el sistema sabe exactamente dónde buscar: extrae el prefijo, sustituye las barras invertidas por barras del sistema operativo, y construye una ruta absoluta precisa. Si el archivo existe, es cargado y el proceso de búsqueda termina. Esta es la esencia de la modularidad y la limpieza en el código moderno.

    <?php
    // --- 1. AUTOLOADING (CARGA AUTOMÁTICA DE CLASES) ---
    // Registramos una función que se ejecutará automáticamente cada vez que PHP
    // necesite cargar una clase que no conoce.
    spl_autoload_register(function ($class) {

        // Mapeo de "namespaces" a directorios (según el estándar PSR-4).
        $prefixes = [
            'App\\'  => BASE_PATH . '/app/',
            'Core\\' => BASE_PATH . '/core/',
        ];

        // Recorremos el mapa para encontrar el prefijo que corresponde a la clase buscada.
        foreach ($prefixes as $prefix => $base_dir) {

            // Comparamos el inicio del nombre de la clase con el prefijo.
            $len = strlen($prefix);
            if (strncmp($prefix, $class, $len) !== 0) {
                // Si no coincide, pasamos al siguiente prefijo del mapa.
                continue;
            }

            // Si coincide, construimos la ruta al archivo.
            $relative_class = substr($class, $len); // Quitamos el prefijo.
            // Reemplazamos las barras invertidas del namespace por las del sistema de archivos.
            $file = $base_dir . str_replace('\\', '/', $relative_class) . '.php'; 

            // Si el archivo existe en la ruta construida, lo cargamos y salimos.
            if (file_exists($file)) {
                require $file;
                return; 
            }
        }
    });

    Para ilustrar la función del autocargador, imaginemos que más adelante en nuestro código, concretamente en la clase Router, necesitamos instanciar el controlador de la página de inicio. El código que se ejecutaría sería algo como:

    // El Router decide que debe cargar el HomeController
$controlador = new App\controller\HomeController();

    En el instante en que PHP encuentra esta línea, se da cuenta de que no conoce la clase App\controller\HomeController. En lugar de lanzar un error fatal, PHP invoca la función anónima que registramos con spl_autoload_register. El proceso interno que se desencadena es el siguiente:

    1. La variable $class dentro de la función anónima recibe el valor 'App\controller\HomeController'.
    2. El código entra en el bucle foreach y comprueba el primer prefijo del mapa, que es 'App\\'.
    3. La función strncmp compara este prefijo con el inicio de la clase solicitada, y como la comparación es exitosa (devuelve 0), el código avanza.
    4. A continuación, substr elimina el prefijo ('App\\') de la clase, dejando la clase relativa en $relative_class = 'controller\HomeController'.
    5. Inmediatamente, str_replace convierte las barras invertidas de esta cadena en barras diagonales, y se concatena la ruta base con la extensión .php, generando la variable $file con el valor final 'BASE_PATH/app/controller/HomeController.php'.
    6. El script comprueba si file_exists es verdadero para esa ruta y, si lo es, require $file; carga el archivo.
    7. En ese momento, PHP obtiene la definición de la clase HomeController y la ejecución de la aplicación continúa con normalidad.
    8. Si la clase solicitada hubiera sido, por ejemplo, Core\Container, el bucle simplemente habría fallado en la primera iteración con 'App\\', pero habría encontrado la coincidencia en la segunda iteración con 'Core\\', construyendo y cargando la ruta BASE_PATH/core/Container.php.

    Una vez que las clases pueden ser cargadas, el Front Controller se dedica a inicializar las piezas clave del framework. Primero, se crea el Contenedor (Core\Container), que se convierte en la caja de herramientas central donde almacenaremos objetos complejos (como la conexión a la base de datos).

    Inmediatamente después, se crea el Enrutador, y es crucial que al inyectarle el constructor del Core\Router($container), nos aseguramos de que el Enrutador tenga acceso a todas las dependencias necesarias para instanciar cualquier controlador, implementando así el principio de Inyección de Dependencias.

    Tras esto, cargamos la configuración de rutas desde routes.php y la pasamos al Enrutador mediante addRoutes para que conozca el mapa de la aplicación.

    <?php
    // --- 2. INICIALIZACIÓN DE LA APLICACIÓN (BOOTSTRAPPING) ---

    // 3. CREAR EL CONTENEDOR DE SERVICIOS
    // El contenedor es como una "caja de herramientas" donde guardamos
    // objetos que queremos que estén disponibles en toda la aplicación (ej: la conexión a la BD).
    $container = new Core\Container();

    // 4. CREAR EL ENRUTADOR
    // El enrutador se encargará de dirigir cada petición a su controlador correspondiente.
    // Le pasamos el contenedor para que los controladores puedan usar sus herramientas.
    $router = new Core\Router($container);

    // 4.1. AÑADIR LAS RUTAS AL ENRUTADOR
    // Cargamos el archivo que define qué URI corresponde a qué controlador y método.
    $routes = require BASE_PATH . '/routes.php';
    $router->addRoutes($routes);

    La fase final es la Transferencia de Mando, que es la más sencilla pero la más importante. Recogemos la URI (el texto completo de la URL solicitada por el usuario) a través de $_SERVER['REQUEST_URI'] y se la entregamos al Enrutador. La línea $router->dispatch($uri) es el punto de no retorno. En ese momento, index.php ha cumplido su misión; ha configurado el entorno, ha cargado las herramientas y ha entregado la llave de la petición al verdadero motor de la aplicación: el Enrutador, que a partir de aquí se encargará de mapear la URI a la clase y al método correctos.

    <?php
    // 5. OBTENER LA URI DE LA PETICIÓN
    // `$_SERVER['REQUEST_URI']` contiene la URL que el usuario ha solicitado (ej: "/perfil/1").
    $uri = $_SERVER['REQUEST_URI'];

    // 6. DESPACHAR LA PETICIÓN
    // Le pasamos la URI al enrutador para que busque una coincidencia, cree el
    // controlador y ejecute el método correspondiente. Aquí es donde la "magia" ocurre.
    $router->dispatch($uri);

    El Cerebro Logístico: La Clase Router

    Si el index.php es el portero, el Enrutador es el jefe de logística. Su trabajo es tomar la petición que el portero le ha pasado y decidir exactamente quién debe atenderla. En nuestro archivo core/Router.php, definimos esta clase esencial que actúa como intermediaria entre la URL del navegador y nuestros controladores.

    La clase comienza definiendo sus herramientas básicas: una propiedad $routes para almacenar el mapa de direcciones (cargado desde routes.php) y, crucialmente, una propiedad $container.

    En el constructor, recibimos y almacenamos este Contenedor de Servicios. Esto es vital porque el enrutador no solo decide qué controlador llamar, sino que también es responsable de construirlo, y para ello necesitará acceder a las dependencias (como la base de datos) que viven dentro del contenedor.

    <?php
    namespace Core;

    class Router
    {
        private $container; // Almacena el contenedor de servicios.
        private $routes = []; // Almacena la lista de rutas permitidas.

        // Recibimos el contenedor al nacer para poder usarlo más tarde.
        public function __construct(Container $container)
        {
            $this->container = $container;
        }

        // Método simple para cargar el array de rutas desde el exterior.
        public function addRoutes(array $routes)
        {
            $this->routes = $routes;
        }
    // ...

    El corazón operativo de la clase es el método dispatch($uri). Este método es el que llamamos desde el index.php y recibe la URL "sucia" que viene del servidor. La primera tarea de dispatch es la higiene y normalización: utiliza parse_url para ignorar cualquier parámetro GET (como ?busqueda=php) y quedarse solo con la ruta, y rtrim para eliminar barras finales que podrían causar duplicidad (haciendo que /perfil/ y /perfil sean lo mismo). Si tras esta limpieza la ruta queda vacía, asumimos que el usuario quiere ir a la raíz (/).

    Con la URI limpia, el enrutador comienza a iterar sobre su lista de rutas conocidas buscando una coincidencia. Aquí surge un desafío: ¿cómo distinguimos una ruta estática como /contacto de una ruta dinámica como /perfil/15? La respuesta es el uso de Expresiones Regulares.

    Dentro del bucle, el enrutador llama a un método auxiliar privado llamado getRoutePattern que transforma nuestras rutas legibles (ej. /perfil/{id}) en patrones complejos de búsqueda (ej. #^/perfil/(?P<id>[^/]+)$#).

    <?php
    public function dispatch($uri)
    {
        // 1. Normalización: Limpiamos la URI para evitar confusiones.
        $uri = parse_url($uri, PHP_URL_PATH);
        $uri = rtrim($uri, '/');
        if ($uri === '') {
            $uri = '/';
        }

        // 2. Búsqueda: Recorremos todas las rutas registradas.
        foreach ($this->routes as $route => $handler) {
            // Convertimos la ruta "humana" en un patrón Regex para poder comparar.
            $pattern = $this->getRoutePattern($route);

            // Usamos preg_match para ver si la URI actual encaja en el patrón.
            if (preg_match($pattern, $uri, $matches)) {
                // ... (Lógica de coincidencia encontrada)
            }
        }

        // Si termina el bucle sin coincidencia, mostramos error 404.
        http_response_code(404);
        echo "<h1>404 - Página no encontrada</h1>";
    }

    Cuando preg_match confirma que la URI del usuario coincide con una de nuestras rutas, entramos en la fase de Resolución y Ejecución.

    Primero, extraemos los parámetros dinámicos de la URL (como el 15 de /perfil/15) filtrando los resultados de la búsqueda para quedarnos solo con los valores nombrados.

    A continuación, preparamos el controlador: construimos el nombre completo de la clase (añadiendo el namespace App\controller\), y aquí es donde brilla la Inyección de Dependencias. No hacemos un simple new Controller(), sino que pedimos al $container que nos dé la conexión a la base de datos (getDatabase()) y se la pasamos al controlador al instanciarlo (new $controllerName($database)).

    Finalmente, utilizamos la función nativa call_user_func_array para ejecutar el método específico del controlador, pasándole los parámetros que extrajimos de la URL. Esto completa el ciclo: el enrutador ha encontrado al responsable, le ha dado las herramientas necesarias y le ha entregado los datos de la petición.

    <?php
    // Dentro del if (preg_match(...)):

    // 3. Extracción de datos: Sacamos los valores de los parámetros (ej: id=1).
    $params = array_filter($matches, 'is_string', ARRAY_FILTER_USE_KEY);

    // 4. Preparación: Determinamos qué clase y método usar.
    $controllerName = 'App\\controller\\' . $handler[0];
    $methodName = $handler[1];

    // 5. Instanciación Inteligente:
    // Usamos el contenedor para obtener la Base de Datos e inyectarla en el controlador.
    $database = $this->container->getDatabase();
    $controller = new $controllerName($database);

    // 6. Ejecución: Llamamos al método del controlador enviándole los parámetros.
    call_user_func_array([$controller, $methodName], $params);

    return; // Misión cumplida, salimos del dispatch.

    Para finalizar la comprensión del enrutador, debemos observar el método auxiliar getRoutePattern, el "traductor" de rutas. Su función es convertir la sintaxis amigable de llaves {} que usamos en routes.php en una expresión regular estricta que PHP pueda entender.

    Utiliza str_replace para escapar las barras de la URL y preg_replace_callback para encontrar cada ocurrencia de {parametro} y sustituirla por un grupo de captura regex (?P<parametro>[^/]+). Este grupo de captura le dice a PHP: "Cualquier cosa que encuentres aquí que no sea una barra, captúralo y guárdalo con este nombre".

    Finalmente, añade anclas de inicio (^) y fin ($) para asegurar que la coincidencia sea exacta (que /perfil/1 coincida, pero /perfil/1/algo no).

    <?php
    private function getRoutePattern($route)
    {
        // Escapamos las barras '/' para la regex.
        $pattern = str_replace('/', '\\/', $route);

        // Convertimos {variable} en grupos de captura regex.
        // Esto transforma '/perfil/{id}' en algo parecido a '/perfil/(?P<id>[^/]+)'
        $pattern = preg_replace_callback(
            '/\{([a-zA-Z_][a-zA-Z0-9_]*)(?::([^\}]+))?\}/',
            function ($matches) {
                $paramName = $matches[1];
                $regex = isset($matches[2]) ? $matches[2] : '[^/]+';
                return '(?P<' . $paramName . '>' . $regex . ')';
            },
            $pattern
        );

        return '#^' . $pattern . '$#';
    }

    El Proveedor Central: Container

    Continuando con el núcleo de nuestro framework, nos encontramos con el Core\Container. Esta clase es la implementación de un Contenedor de Servicios, también conocido como Contenedor de Inyección de Dependencias (DI). Su propósito es centralizar la gestión de las dependencias de la aplicación; en lugar de que cada clase cree manualmente los objetos que necesita (como una conexión a la base de datos), se los pide a este contenedor.

    Es importante entender, tal como se indica en la documentación del archivo, que esta implementación es deliberadamente simple, actuando más como un Localizador de Servicios que como un contenedor de DI completo. Un contenedor avanzado gestionaría el ciclo de vida de los objetos mediante métodos para "registrar" (bind) y "resolver" (resolve) dependencias, pero en nuestro caso, su función es más directa: actuar como un punto de acceso centralizado a los servicios.

    <?php
    namespace Core;

    /**
     * Class Container
     *
     * Un contenedor de servicios (o contenedor de Inyección de Dependencias - DI) es una
     * herramienta que gestiona las dependencias de la aplicación. En lugar de crear
     * objetos (servicios) manualmente donde se necesitan, se piden al contenedor.
     *
     * Esta implementación es muy simple y actúa más como un "Localizador de Servicios".
     * No construye los objetos, sino que delega la obtención de los mismos.
     * Un contenedor más avanzado tendría métodos para "registrar" (bind) y "resolver" (resolve)
     * servicios, gestionando su ciclo de vida.
     */
    class Container
    {
        /**
         * Obtiene la instancia del servicio de base de datos.
         *
         * En esta implementación, el método no crea ni almacena la instancia,
         * sino que delega la llamada al método estático `getInstance()` de la
         * propia clase `Database`.
         *
         * Esto significa que la clase `Database` está implementada como un Singleton,
         * un patrón que asegura que solo exista una única instancia de la clase
         * en toda la aplicación.
         *
         * @return \App\services\Database La única instancia del servicio de base de datos.
         */
        public function getDatabase(): \App\services\Database
        {
            // Devuelve la instancia única del servicio de base de datos.
            return \App\services\Database::getInstance();
        }
    }

    La funcionalidad clave reside en su único método, getDatabase(). Cuando el Router (o cualquier otra parte del sistema) necesita interactuar con la base de datos, no crea una nueva conexión, sino que le pide al contenedor que se la proporcione.

    La clave de esta implementación es la delegación: el Contenedor no sabe cómo construir el objeto Database, sino que confía en la propia clase Database llamando a su método estático getInstance().

    Este nombre de método es la firma clásica del patrón de diseño Singleton. Este patrón garantiza que, sin importar cuántas veces se llame a getInstance(), solo existirá una única instancia de la clase Database en toda la aplicación, evitando así el desperdicio de recursos que supondría abrir múltiples conexiones a la base de datos en una misma petición.

    Por lo tanto, nuestro Contenedor actúa como un intermediario limpio que nos da acceso a ese Singleton.

    El Mapa de la Aplicación: routes.php

    El archivo routes.php es el mapa de carreteras o el directorio telefónico de nuestra aplicación. A diferencia de los archivos lógicos como el Enrutador o el Contenedor, este es un simple archivo de configuración. Su única responsabilidad es devolver un array de PHP que centraliza y define la correspondencia entre la URI (Uniform Resource Identifier) que el usuario escribe en el navegador y la acción específica que debe ejecutar el framework.

    Esta acción, conocida como handler, es a su vez un pequeño array que especifica el nombre de la clase del Controlador y el nombre del método que debe ser invocado. El formato es simple: 'URI_PATTERN' => ['NombreDelControlador', 'nombreDelMetodo']. Es importante notar que el nombre del controlador es solo el nombre de la clase, ya que, como se indica en la documentación, el Enrutador se encarga de añadir automáticamente el prefijo del namespace (App\controller\) al construirlo.

    El verdadero poder de este sistema reside en las rutas dinámicas, que se definen usando la sintaxis de llaves {}. Una ruta como '/perfil/{id}' se convierte en un patrón flexible. El Enrutador es lo suficientemente inteligente como para capturar el valor de ese {id} y pasarlo como argumento al método del controlador correspondiente.

    El sistema incluso permite validaciones avanzadas con expresiones regulares, usando la sintaxis {parametro:regex}, aunque si no se especifica, se usa una regex por defecto que coincide con cualquier cadena que no contenga una barra (/), lo cual es perfecto para la mayoría de los casos.

    <?php
    /**
     * --------------------------------------------------------------------------
     * DEFINICIÓN DE RUTAS DE LA APLICACIÓN
     * --------------------------------------------------------------------------
     *
     * Este archivo centraliza la configuración de todas las rutas de la aplicación.
     * Cada entrada en el array mapea una URI (Uniform Resource Identifier) a un
     * "handler", que es la combinación de un controlador y un método dentro de ese
     * controlador que se encargará de procesar la petición para esa URI.
     *
     * El formato es:
     * 'URI_PATTERN' => ['NombreDelControlador', 'nombreDelMetodo']
     *
     * El 'NombreDelControlador' debe ser el nombre de la clase del controlador
     * (sin el namespace 'App\controller\', ya que el Router lo añade automáticamente).
     *
     * Las rutas pueden incluir parámetros dinámicos encerrados entre llaves `{}`.
     * Por ejemplo, `{id}` o `{nombre}`. Estos parámetros se pasarán como argumentos
     * al método del controlador.
     *
     * Opcionalmente, se puede especificar una expresión regular para un parámetro
     * usando la sintaxis `{parametro:regex}`. Si no se especifica, se usa una
     * regex por defecto que coincide con cualquier cadena que no contenga una barra `/`.
     */

    return [
        // Ruta raíz o página de inicio.
        // Cuando el usuario accede a "/", se ejecuta el método 'index' de 'HomeController'.
        '/' => ['HomeController', 'index'],

        // Otra forma de acceder a la página de inicio.
        '/home' => ['HomeController', 'index'],

        // Ruta para ver el perfil de un usuario específico.
        // `{id}` es un parámetro dinámico que capturará el ID del usuario.
        // El Router pasará este ID como argumento al método 'ver' de 'PerfilController'.
        '/perfil/{id}' => ['PerfilController', 'ver'],

        // Ruta de ejemplo para saludar a alguien con nombre y apellido.
        // `{nombre}` y `{apellido}` son parámetros dinámículos.
        // El Router los pasará como argumentos al método 'saludar' de 'SaludarController'.
        '/saludo/{nombre}/{apellido}' => ['SaludarController', 'saludar'],
    ];

    Al observar el array devuelto, vemos estas reglas en acción. Las rutas '/' y '/home' están mapeadas al mismo método index del HomeController, permitiendo múltiples puntos de entrada para la misma página.

    La ruta '/perfil/{id}' es un ejemplo canónico de un parámetro dinámico; si un usuario visita /perfil/123, el Enrutador capturará '123' y llamará a PerfilController::ver('123').

    Finalmente, la ruta '/saludo/{nombre}/{apellido}' demuestra cómo el sistema puede capturar múltiples parámetros y pasarlos en orden al método del controlador, permitiendo una flexibilidad total en la definición de nuestras URLs.

    El Controlador: El Director de Orquesta

    Ahora que tenemos el Router (el jefe de logística) y el Container (el proveedor de herramientas), llegamos al corazón de la lógica de la aplicación: el Controlador. El Controlador es el "Director de Orquesta" en el patrón MVC. No obtiene los datos (eso es trabajo del Modelo) y no los muestra (eso es trabajo de la Vista); su única misión es coordinar la petición. Recibe la llamada del Enrutador, le pide al Modelo los datos que necesita y, finalmente, le entrega esos datos a la Vista para que los prepare.

    El Controlador Base (Core\Controller)

    Para evitar repetir código, creamos un Controlador Base del cual heredarán todos nuestros controladores. Este archivo, Core\Controller.php, es una clase abstract, lo que significa que no podemos crear una instancia de ella directamente, sino que sirve como plantilla o plano para otros controladores. Su propósito es centralizar la lógica común, como el acceso a la base de datos y la carga de vistas.

    <?php

    namespace Core;

    use App\services\Database;

    /**
     * Class Controller
     *
     * Es una clase base abstracta para todos los controladores de la aplicación.
     * Su propósito es centralizar la lógica común que puedan necesitar los controladores.
     *
     * Al ser 'abstract', no se pueden crear instancias directas de esta clase,
     * solo se puede heredar de ella.
     */
    abstract class Controller
    {
        /**
         * @var Database La instancia del servicio de base de datos.
         * Es 'protected' para que las clases hijas (los controladores concretos) puedan acceder a ella.
         */
        protected $db;

        /**
         * Constructor del controlador.
         *
         * Recibe dependencias (en este caso, el servicio de base de datos) y las
         * almacena para que estén disponibles en los métodos del controlador.
         * Esto es un ejemplo de "Inyección de Dependencias".
         *
         * @param Database $database El servicio de base de datos, inyectado por el Router.
         */
        public function __construct(Database $database)
        {
            $this->db = $database;
        }

        /**
         * Método de ayuda (helper) para cargar una vista.
         *
         * Simplifica la carga de archivos de vista y el paso de datos a las mismas.
         *
         * @param string $viewName El nombre del archivo de la vista (sin la extensión '.view.php').
         * @param array $data Un array asociativo de datos que se deben hacer disponibles en la vista.
         */
        protected function view($viewName, $data = [])
        {
            // La función `extract` es un atajo. Convierte las claves de un array asociativo en variables.
            extract($data);

            // Construimos la ruta completa al archivo de la vista usando la constante VIEWS_PATH
            // y cargamos el archivo.
            require VIEWS_PATH . '/' . $viewName . '.view.php';
        }
    }

    La magia de esta clase base reside en dos sitios. Primero, su constructor: exige que se le pase una instancia de Database. Cuando nuestro Router crea un controlador, primero obtiene la base de datos del Container y se la "inyecta" al controlador, que la almacena en la propiedad protected $db, dejándola disponible para cualquier controlador hijo.

    Segundo, el método view(), que es un ayudante (helper). Este método se encarga del trabajo sucio de cargar un archivo de vista. Lo más importante es que utiliza la función extract($data): si le pasamos un array como ['users' => $listaUsuarios], esta función crea mágicamente una variable $users dentro del ámbito del método, que estará disponible en el archivo de la vista que se carga inmediatamente después con require.

    Un Controlador Concreto: HomeController

    Ahora veamos cómo esta base nos facilita la vida al crear un controlador real, como HomeController.php. Este controlador se encarga de la lógica de nuestra página de inicio, tal como se definió en routes.php.

    <?php
    // Archivo: app/controllers/HomeController.php

    namespace App\controller;

    use App\models\User;
    use Core\Controller;

    class HomeController extends Controller
    {
        public function index()
        {
            // 1. Pedir datos al Modelo (User::all), pasando la conexión a la BD.
            $users = User::all($this->db);

            // 2. Cargar la vista 'home' y pasarle los datos.
            $this->view('home', ['users' => $users]);
        }
    }

    Observe la elegancia y simplicidad de este archivo. Al hacer extends Controller, HomeController hereda automáticamente el constructor y el método view. No necesitamos un constructor aquí; PHP llamará automáticamente al constructor del padre (Core\Controller), el cual recibirá la base de datos inyectada por el Router y la almacenará en $this->db.

    Por lo tanto, dentro de nuestro método index(), podemos acceder libremente a $this->db para pasárselo al modelo User::all(). Una vez que el modelo nos devuelve los datos, simplemente llamamos al método heredado $this->view(), le pasamos el nombre de la vista ('home') y el array de datos que queremos que estén disponibles.

    El controlador ha cumplido su misión de coordinación de forma limpia y con muy poco código.

    El Modelo (El Experto en Datos) y La Vista (El Presentador)

    Llegamos a las dos piezas finales de nuestro patrón MVC: el Modelo y la Vista. Si el Controlador es el director de orquesta, el Modelo es el músico experto (el especialista en datos) y la Vista es el decorador del escenario (el especialista en presentación).

    El Modelo

    El Modelo es la capa de nuestra aplicación que tiene la única responsabilidad de interactuar con la base de datos. Toda la lógica de negocio relacionada con los datos —obtener, guardar, actualizar o eliminar— debe residir aquí. Esto aísla nuestro SQL del resto de la aplicación, permitiendo que nuestros Controladores permanezcan limpios y agnósticos sobre cómo se obtienen los datos.

    En nuestro framework didáctico, el modelo User se implementa con métodos static. Esta es una elección de diseño simple que nos permite llamar a sus métodos directamente sin instanciar un objeto User, pasando la conexión a la base de datos que el Controlador ya posee como dependencia.

        <?php

    namespace App\models;

    use App\services\Database;
    use PDO;

    /**
     * Class User
     *
     * Representa el modelo de usuario en la aplicación.
     * Los modelos son responsables de interactuar con la base de datos
     * para obtener, guardar, actualizar o eliminar datos relacionados con una entidad (en este caso, 'usuarios').
     *
     * Este modelo utiliza métodos estáticos para simplificar el acceso a los datos,
     * recibiendo la instancia de la base de datos como dependencia.
     */
    class User
    {
        /**
         * Obtiene todos los usuarios de la base de datos.
         *
         * @param Database $db La instancia del servicio de base de datos.
         * @return array Un array de objetos `stdClass`, donde cada objeto representa un usuario.
         */
        public static function all(Database $db)
        {
            $pdo = $db->getConnection(); // Obtiene la conexión PDO.
            $stmt = $pdo->query('SELECT * FROM users'); // Ejecuta una consulta para seleccionar todos los usuarios.

            // `fetchAll(PDO::FETCH_OBJ)` devuelve un array de objetos genéricos (stdClass),
            // donde las propiedades del objeto corresponden a los nombres de las columnas.
            return $stmt->fetchAll(PDO::FETCH_OBJ);
        }

        /**
         * Obtiene un usuario específico por su ID.
         *
         * @param Database $db La instancia del servicio de base de datos.
         * @param int $id El ID del usuario a buscar.
         * @return object|false Un objeto `stdClass` que representa al usuario, o `false` si no se encuentra.
         */
        public static function find(Database $db, $id)
        {
            $pdo = $db->getConnection(); // Obtiene la conexión PDO.

            // Prepara una consulta SQL para evitar inyecciones SQL.
            // `:id` es un marcador de posición para el valor del ID.
            $stmt = $pdo->prepare('SELECT * FROM users WHERE id = :id');

            // Ejecuta la consulta, pasando el valor del ID al marcador de posición.
            $stmt->execute(['id' => $id]);

            // `fetch(PDO::FETCH_OBJ)` devuelve un único objeto genérico (stdClass)
            // o `false` si no se encuentra ninguna fila.
            return $stmt->fetch(PDO::FETCH_OBJ);
        }
    }

    Al analizar los métodos, vemos dos prácticas cruciales. En all(), utilizamos fetchAll(PDO::FETCH_OBJ). Esto es fundamental, ya que le dice a PDO que devuelva los resultados no como arrays asociativos, sino como un array de objetos stdClass genéricos, donde cada columna de la tabla es una propiedad pública. Esto nos permitirá en la Vista usar una sintaxis limpia como $user->name.

    En find(), vemos una práctica de seguridad esencial: el uso de consultas preparadas (prepare y execute). Al usar marcadores de posición (:id) en lugar de concatenar el $id directamente en el SQL, prevenimos el tipo de ataque más común en la web: la Inyección SQL.

    La Vista

    Una vez que el Modelo ha extraído los datos y el Controlador se los ha pasado, estos deben ser presentados al usuario. Aquí es donde entra la Vista. La Vista es la capa de presentación; idealmente, no debería contener lógica de negocio, sino solo la lógica de presentación necesaria para mostrar los datos. Es un archivo (en este caso, HTML con incrustaciones de PHP) que actúa como una plantilla.

        <!DOCTYPE html>
    <html>
    <head>
        <title><?= $pageTitle ?></title>
        <link rel="stylesheet" href="/css/style.css">
    </head>
    <body>
    <div class="container">
        <h1>Página de Inicio</h1>
        <p>Bienvenido a la página de inicio.</p>

        <hr>

        <h2>Listado de Usuarios</h2>
        <?php if (isset($users) && !empty($users)): ?>
            <ul>
                <?php foreach ($users as $user): ?>
                    <li>
                        <a href="/perfil/<?php echo $user->id; ?>">
                            <?php echo htmlspecialchars($user->name); ?>
                        </a>
                    </li>
                <?php endforeach; ?>
            </ul>
        <?php else: ?>
            <p>No se encontraron usuarios.</p>
        <?php endif; ?>
    </div>
    </body>
    </html>

    La magia aquí ocurre gracias al método view() de nuestro Controller base. La llamada extract($data) que hicimos en el controlador ha convertido las claves del array de datos en variables locales. Por eso, la vista puede acceder directamente a $users (y a $pageTitle, si se hubiera pasado) como si siempre hubieran existido.

    La vista comprueba si $users existe e itera sobre él con un foreach. Aquí vemos el contrato perfecto con el Modelo: como el Modelo usó PDO::FETCH_OBJ, la Vista accede a los datos usando la sintaxis de objeto ($user->id, $user->name).

    Finalmente, se aplica otra práctica de seguridad vital: htmlspecialchars($user->name). Esto previene ataques de Cross-Site Scripting (XSS), asegurando que si un nombre de usuario contiene código HTML o JavaScript malicioso, se muestre como texto inofensivo en lugar de ejecutarse en el navegador del visitante.

    Con la creación de enlaces dinámicos como /perfil/<?php echo $user->id; ?>, la Vista completa el ciclo, creando URLs que el Router estará esperando para iniciar la siguiente petición.

    Formularios

    Ahora que hemos visto las rutas, los controladores y las vistas de forma individual, es el momento de unirlos para gestionar una de las interacciones más comunes en la web: el envío de un formulario. Laravel proporciona un flujo de trabajo seguro y elegante para manejar todo el proceso, desde la visualización del formulario hasta la validación y el almacenamiento de los datos.

    Crear un nuevo árticulo

    En este apartado vamos a construir el proceso completo para crear un nuevo "artículo" en un blog. Definiremos las rutas, el controlador y las vistas para que se cree este nuevo "articulo".

    Definir las Rutas

    Para gestionar la creación de un nuevo recurso, como un artículo de un blog, es fundamental separar la acción de mostrar el formulario de la acción de procesar los datos enviados. Esta separación de intereses es un principio clave en la arquitectura web y se implementa definiendo dos rutas distintas que responden a dos verbos HTTP diferentes.

    La primera ruta es la que el usuario visita para ver el formulario de creación. Como esta es una operación de solo lectura (el usuario está solicitando ver una página), se utiliza el verbo GET. Su única responsabilidad es apuntar a un método en el controlador (convencionalmente llamado create) que, a su vez, devolverá la vista de Blade que contiene el formulario HTML.

    <?php 
    // En routes/web.php

    // Cuando un usuario visita /articulos/crear con el método GET,
    // se llama al método 'create' del ArticuloController.
    Route::get('/articulos/crear', [ArticuloController::class, 'create'])->name('articulos.create');
?>

    La segunda ruta es el endpoint al que el formulario envía sus datos. Como esta operación crea un nuevo recurso en el servidor, se utiliza el verbo POST. Esta ruta apunta a un método diferente en el mismo controlador (convencionalmente llamado store), que se encargará de validar los datos, guardarlos en la base de datos y redirigir al usuario.

    <?php 
    // En routes/web.php

    // Cuando se envía un formulario con el método POST a /articulos,
    // se llama al método 'store' del ArticuloController.
    Route::post('/articulos', [ArticuloController::class, 'store'])->name('articulos.store');
?>

    Al definir ambas rutas, hemos creado un flujo de trabajo claro: una URL para ver el formulario y otra para procesarlo. El uso de rutas nombradas (->name(...)) es una práctica muy recomendada, ya que nos permite generar URLs en nuestras vistas (p. ej., <form action="{{ route('articulos.store') }}">) sin tener que escribir la URL completa. Si en el futuro decidimos cambiar la URL /articulos a /blog, solo tendremos que cambiarlo en el fichero de rutas y todos los enlaces generados con la función route() se actualizarán automáticamente.

    Crear el Controlador

    Una vez que hemos generado el ArticuloController con Artisan y hemos definido las rutas para que apunten a él, nuestro siguiente paso es rellenar los métodos create() y store() con la lógica necesaria. Estos dos métodos trabajan en pareja para gestionar el proceso de creación de un nuevo recurso.

    La responsabilidad del método create() es extremadamente simple y específica: mostrar al usuario el formulario HTML para crear un nuevo artículo. No procesa datos ni interactúa con la base de datos. Su único trabajo es devolver la vista correspondiente.

    <?php
    // En app/Http/Controllers/ArticuloController.php

    /**
     * Muestra el formulario para crear un nuevo artículo.
     */
    public function create()
    {
        // La función view() busca el fichero en:
        // resources/views/articulos/create.blade.php
        return view('articulos.create');
    }
?>

    Cuando un usuario visita la URL GET /articulos/crear, esta es la función que se ejecuta, devolviendo el formulario que hemos diseñado en Blade.

    Por su parte, el método store() se encarga de recibir los datos enviados por el formulario (a través de una petición POST), validarlos, guardarlos en la base de datos y redirigir al usuario.

    <?php
    // En app/Http/Controllers/ArticuloController.php

    /**
     * Almacena el nuevo artículo en la base de datos.
     */
    public function store(Request $request)
    {
        // 1. Validar los datos del formulario
        $datosValidados = $request->validate([
            'titulo' => 'required|string|max:255',
            'contenido' => 'required|string',
        ]);

        // 2. Lógica para guardar en la BBDD (lo veremos con Eloquent)
        // Articulo::create($datosValidados);

        // 3. Redirigir con un mensaje de éxito
        return redirect()->route('articulos.index') // Redirigir a una ruta nombrada
            ->with('success', '¡Artículo creado con éxito!');
    }
?>

    El proceso dentro del método store comienza con la inyección de dependencias, donde Laravel nos proporciona automáticamente un objeto Request que encapsula toda la información de la petición entrante.

    La primera y más crítica acción que realizamos con este objeto es la validación, utilizando el método $request->validate(). Si los datos enviados por el usuario no cumplen con las reglas definidas, Laravel detiene la ejecución y redirige automáticamente al usuario de vuelta al formulario, mostrando los errores.

    Si la validación es exitosa, el código continúa y pasamos a la lógica de guardado, que es el punto donde el controlador interactúa con el Modelo (p. ej., Articulo::create(...)) para persistir los datos ya validados en la base de datos.

    Finalmente, tras una operación de escritura exitosa, la mejor práctica es realizar una redirección con un mensaje flash. En lugar de devolver una vista, se redirige al usuario a otra página (como la lista de artículos) y se adjunta un mensaje de éxito a la sesión con el método ->with(), el cual estará disponible únicamente en la siguiente petición para confirmar que la operación se ha completado.

    Construyendo la Vista del Formulario en Blade

    El fichero de Blade es donde se define la interfaz con la que interactuará el usuario. En Laravel, la construcción de formularios es un proceso muy asistido, con directivas específicas que mejoran tanto la seguridad como la experiencia de usuario. Analicemos en detalle el código del fichero resources/views/articulos/create.blade.php.

    <h1>Crear Nuevo Artículo</h1>

<form action="{{ route('articulos.store') }}" method="post">

    @csrf

    <div>
        <label for="titulo">Título:</label>
        <input type="text" id="titulo" name="titulo" value="{{ old('titulo') }}">

        @error('titulo')
            <div style="color: red;">{{ $message }}</div>
        @enderror
    </div>

    <br>

    <div>
        <label for="contenido">Contenido:</label>
        <textarea id="contenido" name="contenido">{{ old('contenido') }}</textarea>

        @error('contenido')
            <div style="color: red;">{{ $message }}</div>
        @enderror
    </div>

    <br>

    <button type="submit">Guardar Artículo</button>
</form>

    Este formulario, aunque simple, contiene tres elementos cruciales proporcionados por Blade que son la base de todos los formularios en Laravel.

    Para garantizar la seguridad, Laravel exige el uso de la directiva @csrf como una medida obligatoria y no negociable en cualquier formulario que envíe datos a través de POST, PUT, PATCH o DELETE. Esta directiva genera un campo input oculto con un "token" de seguridad único y secreto que se asocia a la sesión del usuario. Al recibir la petición, Laravel comprueba que el token enviado coincida con el almacenado, protegiendo así la aplicación contra ataques de tipo Cross-Site Request Forgery (CSRF), en los que un sitio web malicioso podría intentar engañar a un usuario para que envíe peticiones a nuestra aplicación sin su consentimiento.

    Además de la seguridad, Laravel se enfoca en mejorar la experiencia del usuario, especialmente cuando la validación de un formulario falla. En lugar de redirigir a una página en blanco, Laravel devuelve al usuario al formulario y proporciona dos herramientas clave para evitar la frustración. La función old('nombre_campo') recupera el valor que el usuario ya había introducido en un campo, evitando que tenga que volver a escribirlo todo. Complementariamente, la directiva @error('nombre_campo') comprueba si existe un error de validación para un campo específico y, si es así, permite mostrar un mensaje contextual justo al lado del campo que necesita ser corregido, utilizando la variable $message para imprimir el texto del error.

    Redirección y Mensajes Flash

    Observa que en el método store(), después de procesar los datos, no devolvemos una vista. En su lugar, redirigimos al usuario a otra página. Este es el patrón estándar Post/Redirect/Get (PRG), que previene el reenvío de formularios si el usuario recarga la página.

    El método ->with('success', '...') encadena una variable flash de sesión. Es un dato que se guarda en la sesión solo para la siguiente petición. Se usa para mostrar mensajes de éxito o error después de una redirección. En la vista de destino, podrías mostrarlo así:

    @if (session('success'))
    <div class="alerta-exito">
        {{ session('success') }}
    </div>
@endif

    Edición de Datos con Formularios: El Flujo de Actualización

    Después de crear registros, el siguiente paso lógico en cualquier aplicación CRUD es la edición de datos. El flujo de actualización es un poco más complejo que el de creación, ya que implica dos pasos: primero, obtener los datos existentes para mostrarlos en un formulario y, segundo, procesar los cambios enviados.

    Las Rutas para Editar y Actualizar

    Necesitamos dos nuevas rutas: una para mostrar el formulario de edición (GET) y otra para procesar los cambios (PUT o PATCH). Si estamos siguiendo las convenciones de un controlador de tipo recurso, estas rutas ya están definidas.

    <?php
    use App\Http\Controllers\ArticuloController;

    // ... (rutas create y store) ...

    // Ruta GET para mostrar el formulario con los datos de un artículo específico
    Route::get('/articulos/{articulo}/editar', [ArticuloController::class, 'edit'])->name('articulos.edit');

    // Ruta PUT para procesar la actualización de un artículo específico
    Route::put('/articulos/{articulo}', [ArticuloController::class, 'update'])->name('articulos.update');
?>

    Cuando definimos rutas para editar o actualizar, como /articulos/{articulo}/editar, el segmento {articulo} es un parámetro de ruta. Su función es identificar de forma única qué recurso queremos modificar. El método tradicional, y el que se usaría en un framework más simple, sería capturar este valor como un simple ID y luego buscar manualmente el recurso en la base de datos.

    Definir el controlador

    Una vez definidas las rutas en routes/web.php, el siguiente paso es implementar la lógica correspondiente dentro de nuestro ArticuloController. Para el flujo de edición, necesitamos dos métodos que trabajarán en pareja: edit, para mostrar el formulario, y update, para procesar los cambios.

    // app/Http/Controllers/ArticuloController.php
<?php

    namespace App\Http\Controllers;

    use Illuminate\Http\Request;
    // Suponemos que tenemos un modelo Articulo
    use App\Models\Articulo;

    class ArticuloController extends Controller
    {
        // ... (métodos create y store) ...

        /**
         * Muestra el formulario para editar un artículo existente.
         */
        public function edit(Articulo $articulo)
        {
            // Gracias al Route Model Binding, Laravel ya nos da el artículo encontrado por su ID.
            // Pasamos el artículo a la vista para rellenar el formulario.
            return view('articulos.edit', ['articulo' => $articulo]);
        }

        /**
         * Actualiza el artículo en la base de datos.
         */
        public function update(Request $request, Articulo $articulo)
        {
            // 1. Validar los datos (similar al método store).
            $datosValidados = $request->validate([
                'titulo' => 'required|string|max:255',
                'contenido' => 'required|string',
            ]);

            // 2. Actualizar el modelo con los datos validados.
            $articulo->update($datosValidados);

            // 3. Redirigir con un mensaje de éxito.
            return redirect()->route('articulos.index') // Redirigir a la lista de artículos
                ->with('success', '¡Artículo actualizado con éxito!');
        }
    }
?>

    La Vista del Formulario de Edición (edit.blade.php)

    Esta vista es muy parecida al formulario de creación, pero con dos diferencias clave: la acción del formulario apunta a la ruta de actualización y los campos del formulario se rellenan con los datos existentes del artículo.

    <h1>Editar Artículo</h1>

<form action="{{ route('articulos.update', $articulo->id) }}" method="post">

    @csrf

    @method('PUT')

    <div>
        <label for="titulo">Título:</label>
        <input type="text" id="titulo" name="titulo" value="{{ old('titulo', $articulo->titulo) }}">

        @error('titulo')
            <div style="color: red;">{{ $message }}</div>
        @enderror
    </div>

    <br>

    <div>
        <label for="contenido">Contenido:</label>
        <textarea id="contenido" name="contenido">{{ old('contenido', $articulo->contenido) }}</textarea>

        @error('contenido')
            <div style="color: red;">{{ $message }}</div>
        @enderror
    </div>

    <br>

    <button type="submit">Actualizar Artículo</button>
</form>

    Al analizar la vista de edición, observamos varias claves en el código de Blade. Primero, el atributo action del formulario se genera dinámicamente con la función route('articulos.update', $articulo->id), lo que asegura que siempre apunte a la URL correcta para actualizar ese recurso específico.

    A continuación, encontramos la directiva @method('PUT'), que resuelve la limitación de que los formularios HTML solo soportan GET y POST; esta directiva añade un campo oculto que le indica a Laravel que debe tratar la petición como si fuera de tipo PUT, una técnica conocida como "simulación de método".

    Finalmente, en los campos del formulario, se utiliza un patrón muy potente: value="{{ old('titulo', $articulo->titulo) }}". Esta función le indica a Blade que primero intente obtener el valor "antiguo" que el usuario había enviado si la validación falló y, si no existe, que utilice como valor por defecto el título actual del artículo, garantizando así que el formulario siempre muestre los datos correctos tanto en la carga inicial como después de un error.

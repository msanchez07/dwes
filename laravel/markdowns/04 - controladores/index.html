    Controladores

    Hasta ahora, hemos definido la lógica de nuestras rutas directamente en el fichero routes/web.php utilizando funciones anónimas (Closures). Esto es útil para rutas muy simples, pero en una aplicación real, se volvería caótico y difícil de mantener. El fichero de rutas debe ser un mapa limpio de las URLs de la aplicación, no el lugar donde reside la lógica de negocio.

    Para resolver esto, movemos toda la lógica de gestión de peticiones a unas clases especiales llamadas Controladores. Un controlador es el "C" en la arquitectura MVC. Actúa como el director de orquesta: recibe la petición del enrutador, se comunica con el Modelo para obtener los datos necesarios y, finalmente, le pasa esos datos a la Vista para que los muestre.

    Creación y Conexión de un Controlador

    El flujo de trabajo para crear y utilizar controladores en Laravel es muy sencillo y se apoya en la potente herramienta de línea de comandos de la que ya hemos hablado: Artisan. Este proceso estandarizado nos asegura que el código esté siempre organizado en el lugar correcto. El ciclo completo se divide en tres pasos claros.

    Paso 1: Crear el Controlador

    Desde la terminal, en la raíz de nuestro proyecto, ejecutamos el siguiente comando de Artisan:

    php artisan make:controller ArticuloController
Laravel creará automáticamente un nuevo fichero en app/Http/Controllers/ArticuloController.php.

    Paso 2: Definir un Método para la Acción

    Dentro de la clase PaginaController que acabamos de generar, definimos un método público para cada acción que queramos que gestione. Por ejemplo, si queremos que este controlador muestre una página de contacto, podríamos crear un método llamado mostrarContacto. Este método contendrá la lógica que antes teníamos en la Closure de la ruta.

    <?php
    namespace App\Http\Controllers;

    use Illuminate\Http\Request;

    class PaginaController extends Controller
    {
        /**
         * Muestra la página de contacto.
         */
        public function mostrarContacto()
        {
            // La lógica podría ser más compleja: obtener datos de un modelo, etc.
            // Por ahora, simplemente devolvemos una vista.
            return view('paginas.contacto');
        }
    }
?>

    Paso 3: Vincular una Ruta al Método del Controlador

    El último paso es modificar nuestro fichero de rutas (routes/web.php) para que, en lugar de ejecutar una Closure, llame al método que acabamos de crear en nuestro controlador.

    Para ello, utilizamos una sintaxis de array donde el primer elemento es la clase del controlador y el segundo es el nombre del método en formato de string. Es una buena práctica importar la clase del controlador al principio del fichero con la sentencia use.

    <?php
    use Illuminate\Support\Facades\Route;
    use App\Http\Controllers\PaginaController; // 1. Importamos la clase

    /* ... otras rutas ... */

    // 2. Definimos la ruta y la vinculamos al método del controlador
    Route::get('/contacto', [PaginaController::class, 'mostrarContacto']);
?>

    Con estos tres pasos, hemos externalizado la lógica de forma limpia. Ahora, cuando un usuario visita /contacto, el enrutador de Laravel sabe que debe instanciar PaginaController y ejecutar su método mostrarContacto para obtener la respuesta.

    Acelerando el Desarrollo: Controladores de Tipo Recurso

    En la mayoría de las aplicaciones web, nuestras interacciones con una entidad o "recurso" (como "Artículos", "Productos" o "Usuarios") siguen el mismo patrón predecible de operaciones CRUD (Crear, Leer, Actualizar, Borrar). Crear la estructura para gestionar estas operaciones puede ser repetitivo: necesitamos una página para mostrar una lista, otra para mostrar un solo elemento, un formulario para crear, otro para editar, y la lógica para procesar cada una de estas acciones.

    Laravel reconoce este patrón y nos ofrece un atajo increíble para agilizar este proceso: los controladores de tipo recurso. El flujo de trabajo es extraordinariamente eficiente. Primero, le pedimos a Artisan que nos genere un controlador especial, pasándole la bandera --resource:

    php artisan make:controller PostController --resource

    Al ejecutar este comando, Laravel no crea un controlador vacío. Genera un fichero app/Http/Controllers/PostController.php con métodos ya definidos (stubs) para cada una de las siete acciones CRUD estándar:

    • index(): Para mostrar una lista de todos los recursos.
    • create(): Para mostrar el formulario de creación de un nuevo recurso.
    • store(): Para guardar el nuevo recurso en la base de datos (procesa el formulario de create).
    • show($id): Para mostrar un único recurso específico.
    • edit($id): Para mostrar el formulario de edición de un recurso existente.
    • update($request, $id): Para guardar los cambios del recurso editado (procesa el formulario de edit).
    • destroy($id): Para eliminar un recurso.

    El segundo paso es registrar todas las rutas necesarias para estas acciones. En lugar de crear siete definiciones de ruta manually, lo hacemos con una única línea en nuestro fichero routes/web.php:

    <?php 
    // En routes/web.php
    use App\Http\Controllers\PostController;

    Route::resource('posts', PostController::class);
?>

    Esa sola línea de Route::resource() crea automáticamente la siguiente tabla de rutas, siguiendo la convención RESTful:

    Verbo HTTP URI Acción (Método del Controlador) Nombre de la Ruta
    GET /posts index posts.index
    GET /posts/create create posts.create
    POST /posts store posts.store
    GET /posts/{post} show posts.show
    GET /posts/{post}/edit edit posts.edit
    PUT/PATCH /posts/{post} update posts.update
    DELETE /posts/{post} destroy posts.destroy

    Devolviendo Vistas desde el Controlador

    La principal responsabilidad de un método de un controlador, después de interactuar con la lógica de negocio o los modelos, es devolver una respuesta. Para devolver una página HTML, utilizamos la función view(). Esta función se encarga de cargar un fichero de plantilla de Blade, inyectarle los datos que le pasemos y renderizar el resultado final.

    La Función view()

    La función view() es un "helper" global de Laravel que simplifica la creación de una respuesta de tipo Vista. Acepta dos argumentos principales:

    1. El nombre de la vista: Una cadena de texto que indica qué fichero de plantilla debe cargarse desde el directorio resources/views. Se utiliza una notación de puntos para navegar por los subdirectorios. Por ejemplo, view('admin.usuarios.perfil') cargará el fichero resources/views/admin/usuarios/perfil.blade.php.
    2. Los datos para la vista (opcional): Un array asociativo donde cada clave se convierte en una variable disponible dentro de la plantilla de Blade.

    Ejemplo práctico

    Vamos a unir todo lo que hemos aprendido: una ruta que apunta a un controlador, el cual obtiene datos y se los pasa a una vista. Definimos una ruta que captura el ID de un usuario y lo pasa al método show de UsuarioController.

    <?php 
    use App\Http\Controllers\UsuarioController;

    Route::get('/usuarios/{id}', [UsuarioController::class, 'show']);
?>

    El controlador (app/Http/Controllers/UsuarioController.php) busca los datos del usuario (en este caso, simulamos la búsqueda) y los pasa a la vista perfil.

    <?php
    namespace App\Http\Controllers;

    class UsuarioController extends Controller
    {
        public function show($id)
        {
            // En un caso real, buscaríamos el usuario en la base de datos.
            // $usuario = Usuario::findOrFail($id);

            // Para este ejemplo, simulamos los datos.
            $usuario = [
                'id' => $id,
                'nombre' => 'Ana García',
                'email' => 'ana.garcia@email.com',
                'rol' => 'Editora'
            ];

            // Devolvemos la vista 'perfil' y le pasamos los datos del usuario.
            // La clave 'user' se convertirá en la variable $user en Blade.
            return view('perfil', ['user' => $usuario]);
        }
    }
?>

    La vista (resources/views/perfil.blade.php) recibe la variable $user y utiliza la sintaxis de Blade para mostrar sus datos.

    <!DOCTYPE html>
<html lang="es">
    <head>
        <title>Perfil de Usuario</title>
    </head>
    <body>
        <h1>Perfil de {{ $user['nombre'] }}</h1>
        <ul>
            <li><strong>ID:</strong> {{ $user['id'] }}</li>
            <li><strong>Email:</strong> {{ $user['email'] }}</li>
            <li><strong>Rol:</strong> {{ $user['rol'] }}</li>
        </ul>
        <a href="/usuarios">Volver a la lista</a>
    </body>
</html>

    Cuando un usuario visita /usuarios/1 en el navegador, el enrutador activa el método show, que a su vez prepara los datos y renderiza la vista perfil.blade.php, inyectando la información del usuario en el HTML final que se envía al navegador.

    Redirecciones HTTP

    No siempre queremos devolver una vista HTML. Cuando un controlador procesa una acción que modifica datos (como store, update o destroy), la práctica estándar no es mostrar una vista, sino redirigir al usuario a otra URL. Esto previene que, si el usuario recarga la página, el formulario se envíe de nuevo duplicando la operación.

    Laravel ofrece el helper redirect() para gestionar esto de forma fluida.

    Redirección Básica

    La forma más inmediata de redirigir es indicando manualmente la ruta o "path" al que queremos enviar al usuario. El helper global redirect() acepta como primer argumento una cadena de texto que representa la URL destino.

    Si bien es útil para prototipado rápido, esta técnica tiene un inconveniente importante: acopla tu controlador a la estructura de tus URLs. Si mañana decides cambiar la ruta /inicio por /dashboard en tu archivo routes/web.php, tendrás que buscar y reemplazar manualmente todas las redirecciones que apuntaban a /inicio en tu código. Por eso, en rutas internas, se prefiere usar nombres de ruta.

    Sin embargo, existen dos casos donde este método es el estándar:

    1. Redirecciones Externas: Cuando necesitas enviar al usuario fuera de tu aplicación (ej. a una pasarela de pago o a Google).
    2. Volver Atrás: Cuando necesitas devolver al usuario a la página de donde vino (ej. tras un error de formulario).
    <?php
    public function index()
    {
        // A. Redirección interna (Hardcoded)
        // Funciona, pero es frágil ante cambios futuros en las rutas.
        return redirect('/panel/configuracion');

        // B. Redirección Externa
        // Para enviar al usuario a otro sitio web, usamos el método ->away().
        // Esto indica explícitamente que salimos de la aplicación.
        return redirect()->away('https://www.paypal.com/checkout');
    }

    public function store(Request $request)
    {
        // C. Volver a la página anterior (Helper back)
        // Muy útil si la validación falla y queremos devolver al usuario al formulario.
        // ->withInput() repuebla el formulario con lo que el usuario había escrito.
        return back()->withInput();
    }
?>

    Redirección a Rutas con Nombre (Con Parámetros)

    Esta es la forma recomendada. Al utilizar el nombre de la ruta (definido con ->name() en routes/web.php o automáticamente por Route::resource), nuestro código se vuelve más robusto.

    Si la ruta requiere parámetros (por ejemplo, redirigir al detalle de un artículo recién creado), pasamos un array asociativo como segundo argumento.

    <?php
    // Supongamos que tenemos una ruta llamada 'posts.show' definida así:
    // Route::get('/posts/{id}', [PostController::class, 'show'])->name('posts.show');

    public function store(Request $request)
    {
        // 1. Lógica para guardar el post...
        $nuevoId = 15; // Imaginemos que este es el ID generado

        // 2. Redirigimos a la vista detalle de ese post
        // Laravel generará la URL: http://miweb.com/posts/15
        return redirect()->route('posts.show', ['id' => $nuevoId]);
    }
?>

    Redirección con Datos "Flash" (with)

    A menudo, al redirigir, queremos informar al usuario del resultado de la operación (ej: "Usuario creado correctamente"). Como la redirección implica una nueva petición HTTP, las variables normales se pierden.

    Para esto usamos el método with(), que almacena datos en la sesión solo para la siguiente petición.

    <?php

    public function destroy($id)
    {
        // 1. Eliminamos el usuario...

        // 2. Redirigimos a la lista y adjuntamos un mensaje
        return redirect()->route('usuarios.index')
            ->with('exito', 'El usuario ha sido eliminado correctamente.');
    }

?>

    Luego, en nuestra vista Blade (usuarios/index.blade.php), podemos comprobar si existe ese mensaje:

    @if (session('exito'))
    <div class="alert alert-success">
        {{ session('exito') }}
    </div>
@endif

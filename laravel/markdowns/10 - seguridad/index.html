    Seguridad en Laravel

    En nuestro capítulo anterior sobre seguridad en PHP, nos sumergimos en las profundidades de la implementación manual. Vimos que, si bien es posible construir mecanismos de defensa con PHP puro, la carga que recae sobre el desarrollador es inmensa y el margen de error, peligrosamente pequeño. Tuvimos que gestionar directamente el array superglobal $_SESSION, asegurándonos de iniciar y destruir sesiones correctamente. Nos enfrentamos a la responsabilidad de hashear y verificar contraseñas usando password_hash() y password_verify(), y de construir nuestra propia lógica repetitiva en cada página para comprobar si un usuario tenía permiso para acceder. Cada paso era un recordatorio de que un pequeño descuido podía abrir una brecha de seguridad en toda la aplicación. Este enfoque, aunque educativo, no es escalable ni sostenible para proyectos profesionales complejos.

    Aquí es donde un framework como Laravel no solo brilla, sino que se convierte en una herramienta indispensable. Laravel no introduce conceptos de seguridad nuevos; en su lugar, toma los mismos principios fundamentales (hashing, gestión de sesiones, control de acceso) y los envuelve en una arquitectura robusta, probada en batalla por miles de desarrolladores, y presentada a través de una API elegante y expresiva. Este apartado explorará cómo Laravel nos libera de la peligrosa carga del trabajo manual, permitiéndonos definir políticas de seguridad complejas de una manera que es a la vez más segura, más legible y infinitamente más fácil de mantener. Pasamos de construir cada cerradura a mano a tener a nuestra disposición un maestro cerrajero.

    Autenticación: Estableciendo la Identidad del Usuario

    Tras haber analizado la complejidad y los riesgos inherentes a la gestión manual de seguridad en PHP nativo, Laravel nos ofrece un cambio de paradigma mediante la abstracción.

    En este contexto, definimos la Autenticación como el mecanismo encargado estrictamente de verificar la identidad de un usuario. Su función es validar las credenciales presentadas para responder a una única pregunta técnica: "¿Quién eres?".

    A diferencia del enfoque manual, donde el desarrollador es responsable de la criptografía y la gestión del estado, Laravel encapsula estos procesos en una arquitectura robusta y probada. El framework gestiona automáticamente el ciclo de vida de la sesión, el hashing seguro de contraseñas y la protección contra vulnerabilidades comunes (como la fijación de sesión), permitiéndonos implementar sistemas de acceso seguros y escalables casi "fuera de la caja", sin la necesidad de escribir la infraestructura de seguridad desde cero.

    Configuración Básica y Starter Kits

    Aunque el núcleo de autenticación de Laravel (Auth) ya está integrado en el framework, una aplicación web necesita una interfaz visual: formularios de login, registro, recuperación de contraseña, etc. Laravel no impone un diseño específico por defecto, pero ofrece soluciones de "andamiaje" (scaffolding) para acelerar el desarrollo.

    Tenemos dos caminos principales: utilizar los Starter Kits oficiales o construir la interfaz manualmente.

    Los Starter Kits (La Vía Rápida)

    Estos paquetes generan automáticamente todas las rutas, controladores y vistas necesarias para un sistema de autenticación completo y seguro. Son la recomendación estándar para proyectos nuevos, ya que eliminan horas de configuración repetitiva.

    • Laravel Breeze (Minimalismo): Es la implementación más ligera y sencilla. Proporciona un punto de partida limpio con todas las funciones básicas de autenticación.

      • Stack Tecnológico: Utiliza Blade y Tailwind CSS por defecto, lo que facilita su personalización si ya conoces el motor de plantillas de Laravel.
      • Versiones Modernas: Recientemente, Breeze también ofrece versiones "Headless" preconfiguradas para React y Vue (usando Inertia.js) e incluso versiones para APIs.
      • Uso recomendado: Proyectos que requieren una autenticación estándar y que planean personalizar mucho el diseño o crecer orgánicamente.

    • Laravel Jetstream (Ecosistema Completo): Es un kit de diseño de aplicaciones mucho más robusto y opinado. No solo incluye autenticación, sino también funcionalidades de nivel empresarial listas para usar: autenticación de dos factores (2FA), gestión de sesiones de navegador, gestión de equipos (Teams) y soporte para API Tokens (Sanctum).

      • Stack Tecnológico: Te obliga a elegir entre Livewire (para amantes de Blade) o Inertia.js (para amantes de Vue.js).
      • Uso recomendado: Aplicaciones SaaS (Software as a Service) o proyectos complejos que necesitan estas características avanzadas desde el día uno.

    El Modelo de Persistencia

    Independientemente de si usas un kit o lo haces a mano, la configuración predeterminada de Laravel asume una estructura de base de datos estándar.

    El framework incluye de fábrica un modelo App\Models\User y una migración de base de datos (create_users_table) que define la estructura de la tabla users. Esta tabla contiene los campos esenciales como email, password (que almacenará el hash, nunca el texto plano) y remember_token (para la funcionalidad "Recordarme").

    Esta estandarización permite que el sistema de autenticación funcione inmediatamente después de ejecutar las migraciones (php artisan migrate), sin necesidad de configuración adicional.

    Autenticación Manual

    Aunque los Starter Kits aceleran el desarrollo inicial, comprender la implementación manual a través de la fachada Auth es indispensable para cualquier aplicación que requiera flujos personalizados (como login con API externa, login social, o validaciones condicionales complejas).

    Laravel simplifica este proceso reduciendo la verificación de credenciales a una sola línea de código, abstraída detrás de métodos seguros.

    El método Auth::attempt es la puerta de entrada estándar. Acepta un array de pares clave/valor como primer argumento.

    ¿Qué ocurre internamente? Cuando ejecutas este método, Laravel realiza tres pasos de seguridad:

    1. Búsqueda: Busca al usuario en la base de datos usando los campos que no son la contraseña (normalmente email).
    2. Verificación Criptográfica: Si encuentra al usuario, toma la contraseña proporcionada en el formulario (texto plano), la somete al algoritmo de hashing configurado (Bcrypt/Argon2) y compara el resultado con el hash almacenado en la base de datos.
    3. Persistencia: Si los hashes coinciden, inicia una sesión autenticada para ese usuario.
    <?php
    namespace App\Http\Controllers;

    use Illuminate\Http\Request;
    use Illuminate\Support\Facades\Auth;

    class LoginController extends Controller
    {
        public function authenticate(Request $request)
        {
            $credentials = $request->validate([
                'email' => ['required', 'email'],
                'password' => ['required'],
            ]);

            // El segundo parámetro (true/false) controla la cookie "Recordarme"
            $remember = $request->boolean('remember');

            if (Auth::attempt($credentials, $remember)) {

                // CRÍTICO: Prevención de "Session Fixation"
                // Regeneramos el ID de sesión tras el login para invalidar
                // cualquier ID que un atacante pudiera haber interceptado antes.
                $request->session()->regenerate();

                // Redirección Inteligente
                // 'intended' redirige al usuario a la URL que intentaba visitar
                // antes de ser interceptado por el middleware de autenticación.
                return redirect()->intended('/dashboard');
            }

            // Si falla, volvemos atrás con un error genérico (por seguridad)
            // y devolvemos el email para no obligar a reescribirlo.
            return back()->withErrors([
                'email' => 'Las credenciales no coinciden con nuestros registros.',
            ])->onlyInput('email');
        }
    }
?>

    Existen escenarios donde ya tenemos la instancia del usuario y confiamos en su identidad, por lo que no necesitamos verificar una contraseña. El caso de uso más común es el Registro de Usuarios: una vez que el usuario crea su cuenta exitosamente, queremos que quede logueado automáticamente para reducir la fricción, sin pedirle que ingrese sus credenciales nuevamente.

    Para esto utilizamos Auth::login($user), que recibe una instancia de un modelo Eloquent.

    <?php
    use App\Models\User;
    use Illuminate\Support\Facades\Auth;
    use Illuminate\Support\Facades\Hash;

    public function register(Request $request)
    {
        // 1. Validación
        $validated = $request->validate([/* ... */]);

        // 2. Creación del Usuario
        // Nota: Es responsabilidad nuestra hashear la contraseña aquí.
        $user = User::create([
            'name' => $validated['name'],
            'email' => $validated['email'],
            'password' => Hash::make($validated['password']),
        ]);

        // 3. Autenticación Inmediata ("Login sin contraseña")
        // El usuario entra al sistema directamente.
        Auth::login($user);

        return redirect('/home');
    }
?>

    Además de las acciones de inicio de sesión, la fachada Auth nos proporciona herramientas esenciales para inspeccionar el estado actual del usuario y gestionar su salida.

    Método Descripción y Uso Retorno
    Auth::check() Verifica si existe un usuario autenticado en la petición actual. Es la forma estándar de proteger bloques de código o vistas. bool (true / false)
    Auth::user() Recupera la instancia completa del modelo del usuario autenticado (ej. App\Models\User). Permite acceder a sus propiedades (Auth::user()->email). ?User (Modelo o null)
    Auth::id() Obtiene únicamente la clave primaria (ID) del usuario autenticado. Es ligeramente más eficiente que cargar todo el modelo si solo necesitas el ID para una consulta. int | string | null
    Auth::logout() Cierra la sesión del usuario actual. Limpia los datos de autenticación de la sesión PHP y regenera el ID de sesión por seguridad. void

    Recuperando el Usuario Autenticado

    Una vez que la barrera de seguridad ha sido superada, necesitamos acceder constantemente a los datos del usuario actual para personalizar su experiencia (mostrar su nombre, listar sus pedidos, verificar sus roles).

    Laravel nos ofrece tres vías principales para acceder a esta instancia del modelo User, dependiendo del contexto en el que nos encontremos.

    1. Vía Fachada o Helper (Contexto Global)

    Es la forma más común y funciona en cualquier parte de tu aplicación (Controladores, Modelos, Servicios, Vistas). Puedes usar la clase estática Auth o la función auxiliar auth(). Ambas son equivalentes.

    <?php
    use Illuminate\Support\Facades\Auth;

    // Opción A: Fachada (Más formal)
    $user = Auth::user();

    // Opción B: Helper (Más conciso)
    $user = auth()->user();

    if ($user) {
        // Acceso directo a propiedades del modelo
        return "Hola, " . $user->name . " (Email: " . $user->email . ")";
    }
?>

    2. Vía Request (Contexto HTTP)

    Esta es la forma "arquitectónicamente pura" dentro de los Controladores. Dado que la autenticación es un estado de la petición actual, el objeto $request siempre tiene acceso al usuario que la originó.

    <?php
    namespace App\Http\Controllers;

    use Illuminate\Http\Request;

    class ProfileController extends Controller
    {
        public function show(Request $request)
        {
            // No usamos Auth::user(), sino que se lo pedimos a la petición.
            // Esto es ideal para Unit Testing, ya que es más fácil de simular (mock).

            $user = $request->user();

            return view('profile', ['user' => $user]);
        }
    }
?>

    3. En Plantillas Blade (Contexto de Vista)

    Aunque puedes usar Auth::user() en Blade, Laravel ofrece una directiva mucho más limpia para comprobar si hay alguien logueado y acceder a sus datos sin llenar la vista de condicionales PHP.

    @auth
    <p>Bienvenido, {{ auth()->user()->name }}</p>

    <form action="/logout" method="POST">
        @csrf
        <button>Cerrar Sesión</button>
    </form>
@endauth

@guest
    <a href="/login">Iniciar Sesión</a>
@endguest

    Nota

    Es un error común pensar que inyectar el modelo User en un método del controlador nos dará al usuario logueado.

    // ¡CUIDADO! Esto NO inyecta al usuario logueado.
// Esto activa "Route Model Binding" buscando un ID en la URL.
public function index(User $user) { ... }

    Para obtener al usuario autenticado en el controlador, siempre inyecta Illuminate\Http\Request y usa $request->user().

    Autorización: Definiendo lo que un Usuario Puede Hacer

    Una vez verificada la identidad del usuario (Autenticación), el siguiente componente crítico en la seguridad de la aplicación es la Autorización. Este proceso determina si la entidad autenticada posee los privilegios necesarios para ejecutar una acción específica sobre un recurso dado.

    Laravel implementa un sistema de autorización flexible que permite definir reglas de acceso granulares. Este sistema desacopla la lógica de validación de permisos del flujo de control principal, centralizándola en dos estructuras arquitectónicas primarias: Gates y Policies.

    Gates (Puertas)

    Los Gates (Compuertas) representan el mecanismo de autorización más directo dentro del framework. Se implementan mediante Closures (funciones anónimas) que evalúan si un usuario autenticado cumple con ciertos criterios para ejecutar una acción.

    Desde una perspectiva arquitectónica, los Gates son ideales para validar permisos que tienen un alcance global o que no están vinculados a una instancia específica de un modelo (por ejemplo, verificar roles administrativos o acceso a áreas restringidas del sistema).

    Los Gates se registran habitualmente en el método boot del AppServiceProvider. La función de definición recibe automáticamente la instancia del usuario autenticado ($user) como primer argumento. Si el usuario no está autenticado, el Gate denegará el acceso automáticamente antes de ejecutar el closure.

    <?php
    namespace App\Providers;

    use Illuminate\Support\Facades\Gate;
    use Illuminate\Foundation\Support\Providers\AuthServiceProvider as ServiceProvider;
    use App\Models\User;

    class AuthServiceProvider extends ServiceProvider
    {
        public function boot(): void
        {
            $this->registerPolicies();

            // Definición de un Gate para acceso administrativo
            Gate::define('access-admin-panel', function (User $user) {
                // Retorna true si el usuario cumple la condición
                return $user->role === 'admin';
            });

            // Definición de un Gate con parámetros adicionales
            // Ejemplo: Verificar si un usuario tiene un nivel de suscripción específico
            Gate::define('download-report', function (User $user, int $reportLevel) {
                return $user->subscription_level >= $reportLevel;
            });
        }
    }
?>

    Una vez definidos, Laravel permite evaluar estos permisos desde múltiples contextos (Controladores, Middlewares, Vistas) utilizando una sintaxis fluida.

    Existen dos formas canónicas de invocar un Gate: a través de la fachada Gate o mediante el trait Authorizable que incluye el modelo User.

    <?php
    use Illuminate\Support\Facades\Gate;
    use Illuminate\Http\Response;

    public function index()
    {
        // Opción A: Usando la Fachada Gate
        if (Gate::allows('access-admin-panel')) {
            // Lógica permitida...
        }

        if (Gate::denies('access-admin-panel')) {
            abort(403, 'Acceso no autorizado.');
        }

        // Opción B: Usando el modelo User (Más legible)
        // El método can() busca tanto en Gates como en Policies.
        if (auth()->user()->can('access-admin-panel')) {
            // ...
        }

        // Verificación con parámetros
        if (auth()->user()->can('download-report', 5)) {
            // ...
        }
    }
?>

    Además de esto, Laravel proporciona directivas de compilación específicas para condicionar la renderización de elementos HTML basándose en los permisos del usuario.

    <nav>
    <a href="/home">Inicio</a>

    {{-- Solo se renderiza si el Gate 'access-admin-panel' retorna true --}}
    @can('access-admin-panel')
        <a href="/admin">Panel de Control</a>
    @endcan

    {{-- Directiva inversa --}}
    @cannot('download-report', 5)
        <div class="alert">Necesitas una suscripción superior para descargar esto.</div>
    @endcannot
</nav>

    Un patrón común en aplicaciones empresariales es permitir que un "Super Administrador" tenga acceso total, ignorando las validaciones individuales. Gate::before permite definir una regla que se ejecuta antes que cualquier otro Gate.

    <?php
    // En el método boot() del Provider
    Gate::before(function (User $user, string $ability) {
        if ($user->isSuperAdmin()) {
            return true; // Autoriza inmediatamente cualquier acción
        }
        // Si retorna null, continúa con la verificación normal del Gate
    });
?>

    Policies (Políticas)

    Mientras que los Gates son excelentes para acciones aisladas, las Policies (Políticas) son la solución arquitectónica para gestionar la autorización en torno a entidades complejas. Funcionan como una clase espejo de un Modelo Eloquent: si tienes un modelo Post y un PostController, lo natural es tener una PostPolicy que gestione los permisos de cada operación CRUD (Create, Read, Update, Delete) sobre ese recurso.

    Este enfoque promueve la cohesión del código, manteniendo las reglas de negocio encapsuladas junto al modelo que protegen, en lugar de dispersas en los controladores.

    Laravel facilita la creación de estas clases mediante Artisan. Al utilizar la bandera --model, el comando pre-generará automáticamente los métodos correspondientes a las acciones estándar de un controlador de recursos (view, create, update, delete, restore, forceDelete).

    php artisan make:policy PostPolicy --model=Post

    En versiones modernas de Laravel, no es necesario registrar manualmente las políticas en el AuthServiceProvider si sigues la convención de nombres estándar. Si el modelo está en app/Models/Post y la política en app/Policies/PostPolicy, Laravel resolverá la relación automáticamente.

    Por defecto, si no hay un usuario autenticado, todos los métodos de la política devuelven false automáticamente (ni siquiera se ejecutan). Si deseas permitir el acceso a invitados (por ejemplo, para la acción view), debes declarar el argumento de usuario como opcional (?User $user).

    <?php

namespace App\Policies;

use App\Models\Post;
use App\Models\User;
use Illuminate\Auth\Access\HandlesAuthorization;

class PostPolicy
{
    use HandlesAuthorization;

    /**
     * FILTRO PREVIO (Gate::before)
     * Se ejecuta antes que cualquier otra regla de esta política.
     * * @param User $user El usuario autenticado.
     * @param string $ability El nombre del método que se intenta ejecutar (ej: 'update').
     * @return bool|null Devuelve true para autorizar inmediatamente, o null para continuar.
     */
    public function before(User $user, string $ability): bool|null
    {
        if ($user->hasRole('admin')) {
            return true; // El administrador tiene acceso total ("God Mode")
        }

        // Si retorna null, la ejecución continúa hacia el método específico (update, view, etc.)
        return null; 
    }

    /**
     * Determina si el usuario puede ver el LISTADO de posts (index).
     * El tipo ?User indica que el usuario es opcional (permite invitados).
     */
    public function viewAny(?User $user): bool
    {
        return true; // El blog es público, cualquiera puede ver el índice.
    }

    /**
     * Determina si el usuario puede ver un post ESPECÍFICO (show).
     */
    public function view(?User $user, Post $post): bool
    {
        if ($post->is_published) {
            return true;
        }

        // Si es un borrador, solo el dueño (autenticado) puede verlo.
        return $user !== null && $user->id === $post->user_id;
    }

    /**
     * Determina si el usuario puede CREAR posts.
     * No recibe una instancia de Post porque aún no existe.
     */
    public function create(User $user): bool
    {
        // Regla de negocio: Solo usuarios con email verificado pueden publicar.
        return $user->hasVerifiedEmail();
    }

    /**
     * Determina si el usuario puede ACTUALIZAR el post.
     */
    public function update(User $user, Post $post): bool
    {
        // Regla de propiedad: Solo el autor puede editar su propio contenido.
        return $user->id === $post->user_id;
    }

    /**
     * Determina si el usuario puede ELIMINAR el post (Soft Delete).
     */
    public function delete(User $user, Post $post): bool
    {
        // Misma lógica: solo el autor puede enviarlo a la papelera.
        return $user->id === $post->user_id;
    }

    /**
     * Determina si el usuario puede RESTAURAR un post eliminado.
     * Solo aplica si usas SoftDeletes en tu modelo.
     */
    public function restore(User $user, Post $post): bool
    {
        return $user->id === $post->user_id;
    }

    /**
     * Determina si el usuario puede ELIMINAR PERMANENTEMENTE el post.
     * (Vaciar de la papelera / Hard Delete).
     */
    public function forceDelete(User $user, Post $post): bool
    {
        // Regla estricta: Incluso el dueño tiene prohibido borrar físicamente el registro.
        // Solo los administradores (capturados en el método 'before') pueden hacer esto.
        return false;
    }
}
?>

    Existen múltiples puntos de entrada para invocar estas reglas de autorización, dependiendo de la capa de la aplicación en la que te encuentres. El método authorize (disponible en los controladores que extienden de App\Http\Controllers\Controller) infiere automáticamente qué política usar basándose en el modelo pasado como argumento.

    <?php
    public function update(Request $request, Post $post)
    {
        // Busca PostPolicy, ejecuta el método 'update' pasando ($user, $post).
        // Si falla, lanza automáticamente una HttpResponseException (403 Forbidden).
        $this->authorize('update', $post);

        // El flujo solo llega aquí si la autorización fue exitosa.
        $post->update($request->validated());

        return redirect()->route('posts.show', $post);
    }
?>

    También puedes proteger rutas enteras sin siquiera entrar al controlador utilizando el middleware can.

    <?php
    use App\Models\Post;

    // Laravel usa "Route Model Binding" para obtener el post y pasárselo a la Policy.
    Route::put('/post/{post}', [PostController::class, 'update'])
        ->middleware('can:update,post');
?>

    Finalmente para ocultar elementos de la interfaz de usuario (botones de editar/borrar) a usuarios que no tienen permiso para usarlos utilizamos @can.

    <h1>{{ $post->title }}</h1>

<div class="actions">
    @can('update', $post)
        <a href="{{ route('posts.edit', $post) }}" class="btn btn-primary">
            Editar Post
        </a>
    @endcan

    @can('delete', $post)
        <button wire:click="deletePost" class="btn btn-danger">
            Eliminar
        </button>
    @endcan
</div>

    Roles: Integrando Permisos Basados en Roles

    Mientras que los Gates y Policies gestionan permisos granulares ("¿puede editar este post específico?"), los Roles son una abstracción de nivel superior que agrupa esos permisos. Asignar un rol de "Editor" es mucho más eficiente que asignar manualmente 20 permisos individuales a cada usuario.

    En la arquitectura de Laravel, no existe una tabla de roles "nativa" por defecto. Eres tú, como arquitecto, quien decide la complejidad de la implementación según las necesidades del proyecto:

    1. Columna Simple (Jerarquía Plana): Añadir una columna role (string/enum) en la tabla users. Ideal para aplicaciones donde un usuario solo puede ser una cosa a la vez (o es Admin o es Usuario).
    2. Relación Muchos a Muchos (RBAC): Tablas roles, permissions y tablas pivote. Necesario cuando un usuario puede tener múltiples roles simultáneos (ej. ser "Editor" y "Contable" a la vez).

    Para este apartado, implementaremos la estrategia de Columna Simple, que cubre el 80% de los casos de uso habituales.

    Implementación de Roles (Ejemplo Simple)

    Para evitar ensuciar nuestro código con comparaciones de cadenas repetitivas (if ($user->role === 'admin')), centralizamos la lógica en el modelo User.

    Nota

    En PHP 8.1+, se recomienda encarecidamente usar Enums para evitar "Magic Strings", pero para este ejemplo usaremos strings por simplicidad.

    <?php
    namespace App\Models;

    use Illuminate\Foundation\Auth\User as Authenticatable;

    class User extends Authenticatable
    {
        /**
         * Verifica si el usuario tiene un rol específico.
         */
        public function hasRole(string $role): bool
        {
            // Comparación estricta del valor de la columna
            return $this->role === $role;
        }

        /**
         * Helper semántico para verificar privilegios de administrador.
         * Centraliza la lógica: si mañana el rol cambia de 'admin' a 'super-admin',
         * solo cambias este método.
         */
        public function isAdmin(): bool
        {
            return $this->hasRole('admin');
        }
    }
?>

    Uso de Roles en Gates

    Los Roles brillan cuando se combinan con Gates para definir barreras arquitectónicas amplias.

    <?php
    // En app/Providers/AuthServiceProvider.php
    use Illuminate\Support\Facades\Gate;
    use App\Models\User;

    public function boot(): void
    {
        // Definimos un Gate que agrupa múltiples roles
        Gate::define('access-backend', function (User $user) {
            return $user->hasRole('admin') || $user->hasRole('editor');
        });

        // Gate crítico restringido solo a administradores
        Gate::define('manage-system-settings', function (User $user) {
            return $user->isAdmin();
        });
    }
?>

    Uso de Roles en Policies

    Uno de los patrones más potentes es utilizar los roles para "bypassear" (saltar) las reglas granulares. Si tienes un Administrador que debe tener control total, no tiene sentido escribir lógica de autorización en cada método (update, delete, etc.).

    Utilizamos el método before de la Policy para interceptar la llamada antes de que llegue a la lógica normal.

    <?php
    namespace App\Policies;

    use App\Models\Post;
    use App\Models\User;

    class PostPolicy
    {
        /**
         * Interceptor Previo.
         * @return bool|null
         * - true: Autoriza inmediatamente (salta el resto de métodos).
         * - false: Deniega inmediatamente.
         * - null: Continúa con la comprobación normal del método solicitado (view, update...).
         */
        public function before(User $user, string $ability): bool|null
        {
            if ($user->isAdmin()) {
                return true; // El admin puede hacer TODO con los posts.
            }

            return null; // El usuario normal debe pasar las validaciones siguientes.
        }

        /**
         * Regla específica para usuarios normales.
         */
        public function update(User $user, Post $post): bool
        {
            // Esta línea solo se ejecuta si el usuario NO es admin.
            return $user->id === $post->user_id;
        }

        /**
         * Ejemplo de combinación: Rol específico + Regla de negocio.
         */
        public function publish(User $user, Post $post): bool
        {
            // Solo los editores pueden publicar, y solo si son dueños del post.
            return $user->hasRole('editor') && $user->id === $post->user_id;
        }
    }
?>

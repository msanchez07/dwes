    Migraciones

    En el desarrollo tradicional de aplicaciones PHP, la gestión de la base de datos solía ser un punto crítico de fricción. Los desarrolladores compartían archivos .sql por correo o chat, intentando sincronizar manualmente los cambios estructurales ("Añadí una columna 'phone' a la tabla usuarios, acuérdate de ejecutar el SQL"). Este enfoque manual es propenso a errores humanos y desastroso en entornos de producción.

    Laravel resuelve este problema introduciendo las Migraciones. Técnicamente, las migraciones actúan como un sistema de control de versiones para tu base de datos (similar a lo que Git es para tu código). Permiten definir y modificar el esquema de la base de datos utilizando código PHP expresivo y agnóstico del motor SQL, en lugar de escribir sentencias CREATE TABLE o ALTER TABLE manualmente.

    La adopción de las migraciones en un proyecto de Laravel aporta tres beneficios arquitectónicos que transforman radicalmente el flujo de trabajo del equipo de desarrollo. En primer lugar, garantizan la Consistencia de Entornos. Al definir la estructura de datos en código, las migraciones actúan como una fuente única de verdad. Esto elimina la discrepancia habitual donde la base de datos local del desarrollador tiene tablas que no existen en el entorno de pruebas (Staging) o, peor aún, en Producción. Al desplegar el código, la estructura de la base de datos viaja con él, asegurando que todos los entornos estén matemáticamente sincronizados.

    En segundo lugar, el sistema ofrece un Agnosticismo de Base de Datos total. Gracias a la capa de abstracción de Laravel, el desarrollador escribe instrucciones en PHP utilizando una sintaxis fluida y expresiva, sin preocuparse por el dialecto SQL subyacente. El framework actúa como un traductor inteligente, convirtiendo ese código PHP en las sentencias SQL específicas para MySQL, PostgreSQL, SQLite o SQL Server según la configuración del entorno. Esto otorga una flexibilidad sin precedentes: permite, por ejemplo, desarrollar en una máquina local ligera usando SQLite y desplegar en un servidor robusto con PostgreSQL, sin tener que reescribir una sola línea de definición de esquema.

    Finalmente, y quizás lo más crítico para la estabilidad del sistema, las migraciones introducen el concepto de Reversibilidad. A diferencia de ejecutar una sentencia SQL manual, que es una acción definitiva y difícil de deshacer, las migraciones están diseñadas como operaciones bidireccionales. Cada cambio estructural incluye no solo las instrucciones para aplicarse, sino también la lógica exacta para revertirse. Esto dota al equipo de una red de seguridad indispensable: si una modificación en la base de datos causa un error crítico en producción, es posible deshacer el cambio (Rollback) de manera programática y segura, devolviendo el sistema a su estado estable anterior en cuestión de segundos.

    Anatomía de una Clase de Migración

    Para materializar estos conceptos, Laravel utiliza una estructura de clases estandarizada. Desde la versión 8.x, el framework ha adoptado el uso de clases anónimas que extienden de Illuminate\Database\Migrations\Migration. Esta decisión de diseño simplifica el código al eliminar la necesidad de asignar nombres únicos de clase a cada archivo, evitando colisiones de nombres en proyectos grandes con cientos de migraciones históricas.

    Dentro de esta estructura, la lógica se divide estrictamente en dos métodos fundamentales que representan el ciclo de vida del cambio. El método up() es el constructor; su responsabilidad es describir los cambios positivos que se aplicarán al esquema, como la creación de nuevas tablas, la adición de columnas o la definición de índices. Es el guion que Laravel ejecuta cuando decidimos avanzar la versión de nuestra base de datos.

    En contraposición, el método down() actúa como el destructor o el mecanismo de reversión. Su función es contener la lógica inversa exacta de lo definido en el método up(). Si el método up() crea una tabla, el método down() debe eliminarla; si añade una columna, este debe retirarla. La implementación rigurosa de este método es crucial, ya que es el único mecanismo que permite al sistema volver a un estado anterior de forma consistente durante una operación de rollback.

    El Schema Builder

    Laravel proporciona la fachada Schema para interactuar con las tablas. Dentro, utilizamos el objeto Blueprint para definir las columnas con una sintaxis fluida y legible.

    Veamos un ejemplo práctico de una migración para crear una tabla de posts:

    <?php

use Illuminate\Database\Migrations\Migration;
use Illuminate\Database\Schema\Blueprint;
use Illuminate\Support\Facades\Schema;

return new class extends Migration
{
    /**
     * Ejecuta las migraciones ("Hacer").
     */
    public function up(): void
    {
        // Schema::create genera la sentencia CREATE TABLE
        Schema::create('posts', function (Blueprint $table) {

            // Definición de columnas
            $table->id(); // Clave primaria auto-incremental (bigint unsigned)

            $table->foreignId('user_id')
                  ->constrained() // Crea la clave foránea referenciando a 'users'
                  ->onDelete('cascade'); // Si se borra el usuario, se borran sus posts

            $table->string('title'); // VARCHAR(255)
            $table->string('slug')->unique(); // Índice único
            $table->text('content'); // TEXT

            $table->boolean('is_published')->default(false); // TINYINT(1) con valor por defecto

            $table->timestamp('published_at')->nullable(); // TIMESTAMP que acepta NULL

            $table->timestamps(); // Crea columnas 'created_at' y 'updated_at' automáticas
            $table->softDeletes(); // Crea columna 'deleted_at' para borrado lógico
        });
    }

    /**
     * Revierte las migraciones ("Deshacer").
     */
    public function down(): void
    {
        // Elimina la tabla si existe
        Schema::dropIfExists('posts');
    }
};
?>

    Ciclo de Vida y Comandos Artisan

    El flujo de trabajo con migraciones se gestiona enteramente desde la consola. Laravel lleva un registro interno (en una tabla de base de datos llamada migrations) de qué archivos ya han sido ejecutados para no repetirlos jamás.

    1. Generación (Make): Crea un nuevo archivo con la marca de tiempo actual en database/migrations. Este comando se utiliza tanto para crear tablas nuevas como para modificar las existentes. php artisan make:migration create_posts_table php artisan make:migration add_votes_to_posts_table --table=posts

    2. Ejecución (Migrate): Aplica los cambios definidos en los métodos up() de todas las migraciones que aún están pendientes. php artisan migrate

    3. Reversión (Rollback): Ejecuta el método down() del último lote de migraciones aplicadas. Es tu "botón de deshacer" si cometes un error en el último despliegue. php artisan migrate:rollback

    4. Reinicio (Fresh): Elimina todas las tablas de la base de datos y vuelve a ejecutar todas las migraciones desde cero. Es destructivo e ideal para limpiar datos basura en el entorno local durante el desarrollo. php artisan migrate:fresh

    Modificando Tablas Existentes

    A medida que tu aplicación evoluciona, necesitarás añadir o modificar columnas en tablas que ya existen. Laravel es lo suficientemente inteligente para detectar tus intenciones si sigues una convención de nombres o usas la bandera --table.

    A diferencia de la creación (Schema::create), para actualizar utilizamos Schema::table.

    <?php
// Ejemplo: php artisan make:migration add_category_to_posts_table --table=posts

public function up(): void
{
    Schema::table('posts', function (Blueprint $table) {
        // Añadimos una columna nueva después de 'content'
        $table->string('category')->after('content')->nullable();
    });
}

public function down(): void
{
    Schema::table('posts', function (Blueprint $table) {
        // Es vital eliminar la columna al revertir
        $table->dropColumn('category');
    });
}
?>

    debes tener en cuenta que añadir columnas nuevas es sencillo, pero modificar una columna que ya existe (por ejemplo, convertir un texto corto en uno largo, o permitir que una columna acepte valores nulos) es una operación mucho más compleja a nivel de base de datos. Cada motor (MySQL, PostgreSQL, SQL Server) tiene una sintaxis muy diferente para ejecutar comandos ALTER TABLE.

    Históricamente, Laravel delegaba la "traducción" de estas modificaciones a una librería externa llamada Doctrine DBAL (Database Abstraction Layer). Esta librería inspecciona el estado actual de tu tabla y genera el SQL exacto necesario para alterarla. Actualmente Laravel ya cuenta con soporte nativo para estos cambios.

    La lógica es intuitiva: defines la columna nuevamente tal y como quieres que quede y encadenas el método ->change() al final. Esto le indica a Laravel: "No intentes crear esta columna, solo modifica la existente para que coincida con esta definición".

    Supongamos que tenemos una columna title creada como string (limitada a 255 caracteres) y queremos ampliarla a 500 caracteres y permitir que sea nula.

    <?php

public function up(): void
{
    Schema::table('posts', function (Blueprint $table) {
        // Redefinimos la columna con los nuevos atributos
        $table->string('title', 500) // Nueva longitud
              ->nullable()           // Ahora acepta NULL
              ->change();            // ¡Aplica los cambios!
    });
}

public function down(): void
{
    Schema::table('posts', function (Blueprint $table) {
        // Es vital revertir los cambios en el método down
        // Volvemos a la longitud original y quitamos el nullable
        $table->string('title', 255)
              ->nullable(false)
              ->change();
    });
}
?>

    El uso de ->change() conlleva riesgos inherentes a la base de datos.

    • Reducción de tamaño: Si cambias una columna de string(100) a string(50), y existen registros con 80 caracteres, la base de datos podría cortar (truncar) la información o lanzar un error, dependiendo de tu configuración estricta.
    • Cambio de Tipo: Cambiar un string a integer fallará si la columna contiene datos alfanuméricos que no se pueden convertir a números.

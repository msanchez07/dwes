    Patrones Avanzados con Async/Await y Optimización de Peticiones

    En los capítulos anteriores hemos visto los fundamentos de AJAX y cómo utilizar fetch() para realizar peticiones asíncronas. En este tema profundizaremos en patrones más avanzados que te permitirán escribir código más robusto, eficiente y mantenible. Dominar estos patrones es esencial para construir aplicaciones web modernas que respondan de forma fluida incluso bajo condiciones adversas, como conexiones lentas o errores temporales.

    La Importancia de los Patrones Asíncronos

    Cuando construimos aplicaciones web modernas, nos enfrentamos a desafíos que no existían en la web tradicional: necesitamos cargar múltiples recursos simultáneamente, manejar errores de red impredecibles, proporcionar feedback instantáneo al usuario, y mantener la aplicación fluida incluso cuando las cosas no salen como esperamos.

    Los patrones que exploraremos en este tema son el resultado de años de experiencia colectiva de la industria resolviendo estos problemas. Cada patrón aborda un problema específico que surge regularmente en el desarrollo de aplicaciones asíncronas.

    Imaginemos que estamos construyendo un dashboard que muestra información del usuario, sus notificaciones, y estadísticas del sistema. Sin los patrones adecuados,haríamos estas tres peticiones secuencialmente, tardando tres veces más de lo necesario. O peor, si la primera falla, nunca sabríamos si las otras tendrían éxito.

    Con Promise.all, podemos hacer las tres peticiones simultáneamente y reducir el tiempo de carga drásticamente. Con Promise.allSettled, podemos mostrar los datos que funcionan aunque otros fallen. Con debounce y throttle, evitamos saturar el servidor con peticiones innecesarias. Cada patrón es una herramienta que nos ayuda a construir aplicaciones más profesionales.

    Repaso: Async/Await

    Antes de entrar en los patrones avanzados, recordemos brevemente la sintaxis async/await, que es la forma moderna y recomendada de trabajar con operaciones asíncronas en JavaScript. Esta sintaxis, introducida en ES2017, nos permite escribir código asíncrono que se lee como si fuera síncrono, facilitando enormemente su comprensión y mantenimiento.

    La palabra clave async se usa para declarar una función que siempre devuelve una Promesa. Dentro de esta función, podemos usar await para pausar la ejecución hasta que una Promesa se resuelva, escribiéndose de forma secuencial y legible. El resultado es un código mucho más intuitivo que evita el anidamiento excesivo de callbacks o el encadenamiento largo de .then().

    Función async básica
    async function obtenerUsuario(id) {
    const respuesta = await fetch(`/api/usuarios/${id}`);
    const datos = await respuesta.json();
    return datos;
}

    En este ejemplo, la función obtenerUsuario es asíncrona porque realiza operaciones de entrada/salida (I/O) que requieren esperar al servidor. La palabra await pausa la ejecución en cada línea hasta que la operación anterior se complete, pero no bloquea el hilo principal del navegador; otros cálculos pueden continuar ejecutándose mientras tanto.

    Por Qué el Manejo de Errores Es Crítico

    Un código que no maneja errores está incompleto y es potencialmente peligroso. Cuando trabajamos con operaciones asíncronas, los errores pueden ocurrir en cualquier punto de la cadena: desde que iniciamos la petición hasta que procesamos la respuesta.

    Los errores en aplicaciones asíncronas son fundamentalmente diferentes a los errores síncronos. Un error síncrono generalmente detiene la ejecución inmediatamente y puede mostrarse al usuario. Un error asíncrono puede pasar desapercibido si no lo manejamos explícitamente, dejando al usuario sin saber qué pasó.

    Existen varios tipos de errores que debemos anticipar:

    Los errores de red ocurren cuando la conexión falla: sin wifi, servidor inaccesible, timeout. El navegador los lanza como excepciones que debemos capturar con catch.

    Los errores HTTP tienen códigos de estado 4xx o 5xx. El servidor está respondiendo, pero la respuesta indica un problema: no encontrado (404), no autorizado (401), error de servidor (500). fetch no lanza excepción para estos, debemos verificar response.ok manualmente.

    Los errores de JSON ocurren cuando la respuesta dice ser JSON pero no lo es: HTML de error del servidor, página de mantenimiento. Al llamar response.json(), el parser falla.

    Los errores de timeout ocurren cuando el servidor tarda demasiado en responder. No son errores nativos de fetch, pero podemos implementarlos.

    Una aplicación profesional debe anticipar todos estos escenarios y responder de forma elegante, informando al usuario sin dejarlo en un estado inconsistente. El usuario nunca debería ver una página "rota" sin explicación.

    Try/Catch en Funciones Async

    La forma más limpia de manejar errores en funciones async/await es utilizando bloques try/catch. Este patrón nos permite encapsular la lógica que puede fallar y definir un comportamiento específico para cuando ocurra un error.

    Manejo de errores con try/catch
    async function cargarDatos() {
    try {
        const respuesta = await fetch('/api/datos');

        if (!respuesta.ok) {
            throw new Error(`Error HTTP: ${respuesta.status}`);
        }

        const datos = await respuesta.json();
        return datos;

    } catch (error) {
        console.error('Error al cargar datos:', error.message);
        return null;
    }
}

    En este código, el bloque try contiene toda la lógica de la petición. Si algo falla, la ejecución salta inmediatamente al bloque catch, donde podemos registrar el error y devolver un valor por defecto (en este caso, null) que el código llamador puede gestionar. Es importante notar que lanzamos nuestro propio error cuando la respuesta HTTP no es satisfactoria (!respuesta.ok), tratando los errores de servidor (404, 500, etc.) de la misma forma que los errores de red.

    Propagación de Errores

    A veces es mejor dejar que el error se propague para que el código llamador lo maneje, especialmente cuando múltiples funciones necesitan acceder al mismo dato y cualquier error debe mostrarse al usuario de la misma forma. En lugar de capturar y ocultar el error, lo lanzamos con throw para que se propague hasta un nivel superior que sepa cómo tratarlo.

    Propagación de errores
    async function obtenerArticulo(id) {
    const respuesta = await fetch(`/api/articulos/${id}`);

    if (!respuesta.ok) {
        throw new Error(`Artículo ${id} no encontrado`);
    }

    return await respuesta.json();
}

async function mostrarArticulo() {
    try {
        const articulo = await obtenerArticulo(123);
        console.log(articulo);
    } catch (error) {
        document.getElementById('error').textContent = error.message;
    }
}

    Aquí, obtenerArticulo no captura el error; simplemente lo lanza. Es mostrarArticulo quien decide qué hacer con él. Este patrón de "fail fast" mantiene cada función con una única responsabilidad y evita duplicar lógica de manejo de errores en múltiples lugares.

    El Bloque finally

    El bloque finally se ejecuta siempre, tanto si hay error como si no. Es útil para limpiar estados de carga, cerrar conexiones o restaurar la interfaz a un estado consistente, independientemente de si la operación tuvo éxito.

    Uso de finally para limpiar recursos
    async function enviarFormulario(datos) {
    const boton = document.getElementById('submit-btn');
    boton.disabled = true;
    boton.textContent = 'Enviando...';

    try {
        const respuesta = await fetch('/api/formulario', {
            method: 'POST',
            body: JSON.stringify(datos)
        });

        if (!respuesta.ok) throw new Error('Error en el envío');

        return await respuesta.json();

    } catch (error) {
        console.error(error);
        throw error;

    } finally {
        boton.disabled = false;
        boton.textContent = 'Enviar';
    }
}

    En este ejemplo, el bloque finally asegura que el botón vuelva a estar habilitado siempre, tanto si la petición fue exitosa como si falló. Sin finally, tendríamos que duplicar la línea de restauración del botón en el try y en el catch.

    Peticiones Paralelas con Promise.all

    Cuando necesitamos hacer varias peticiones independientes, no tiene sentido esperar a que una termine para empezar la siguiente. Imaginemos que estamos construyendo un dashboard que muestra: el perfil del usuario (nombre, avatar, configuración), sus notificaciones pendientes, y estadísticas del sistema. Estas tres piezas de información son completamente independientes entre sí: los datos de uno no dependen de los otros.

    Podemos ejecutarlas en paralelo usando Promise.all(), lo que puede reducir drásticamente el tiempo total de espera. Si cada petición tarda 200ms, hacerlas secuencialmente tardaría 600ms. Haciendolas en paralelo, tardamos solo 200ms (la más lenta).

    Promise.all toma un array de promesas y retorna una sola promesa que se resuelve cuando todas las entradas se han resuelto, o se rechaza si alguna falla.

    Ejemplo: Cargar Dashboard con Múltiples Datos

    Peticiones paralelas con Promise.all
    async function cargarDashboard() {
    try {
        const [usuarios, estadisticas, notificaciones] = await Promise.all([
            fetch('/api/usuarios').then(r => r.json()),
            fetch('/api/estadisticas').then(r => r.json()),
            fetch('/api/notificaciones').then(r => r.json())
        ]);

        renderizarUsuarios(usuarios);
        renderizarEstadisticas(estadisticas);
        renderizarNotificaciones(notificaciones);

    } catch (error) {
        console.error('Error al cargar el dashboard:', error);
    }
}

    Aquí, las tres peticiones se inician simultáneamente. Promise.all espera a que todas se completen y devuelve un array con los resultados en el mismo orden en que se pasaron. Si alguna petición falla, la promesa entera se rechaza y saltamos al catch. El tiempo total será aproximadamente el de la petición más lenta, en lugar de la suma de todas.

    Promise.allSettled: Resultados Parciales

    Si alguna petición falla, Promise.all entero falla. Si queremos obtener los resultados de las que sí funcionaron aunque algunas fallen, podemos usar Promise.allSettled. Este método espera a que todas las promesas se completen (hayan succeed o failed) y devuelve un array de objetos que describen el resultado de cada una.

    Promise.allSettled para resultados parciales
    async function cargarTodoOMostrarErrores() {
    const resultados = await Promise.allSettled([
        fetch('/api/usuarios').then(r => r.json()),
        fetch('/api/datos-externos').then(r => r.json()),
        fetch('/api/config').then(r => r.json())
    ]);

    resultados.forEach((resultado, index) => {
        if (resultado.status === 'fulfilled') {
            console.log(`Petición ${index} exitosa:`, resultado.value);
        } else {
            console.error(`Petición ${index} fallida:`, resultado.reason);
        }
    });
}

    En este ejemplo, aunque la API externa falle, las otras dos peticiones seguirán mostrándose correctamente. Esto es útil para dashboards donde algunos widgets pueden fallar pero otros deben seguir funcionando.

    Por Qué Controlar la Frecuencia de Eventos

    Cuando trabajamos con eventos que se disparan frecuentemente, como keyup en un campo de búsqueda o scroll en una ventana, puede ser contraproducente (o directamente dañino para el rendimiento) hacer una operación por cada evento. Cada vez que el usuario presiona una tecla, se dispara el evento keyup. Un usuario rápido puede escribir 10 letras en un segundo, lo que触发aría 10 peticiones al servidor si verificáramos en cada evento.

    Esto tiene consecuencias graves:

    El servidor recibe demasiadas peticiones, consumiendo recursos innecesarios. Las respuestas pueden llegar fuera de orden: el usuario escribe "gato", pedimos "g", "ga", "gat", "gato", y la respuesta de "g" llega después de la de "gato", mostrando resultados incorrectos.

    La interfaz se vuelve lenta y responsiva porque estamos procesando cada pulsación en lugar de la palabra completa.

    Los navegadores pueden throttle automáticamente las peticiones excesivas, causando comportamiento impredecible.

    Aquí entran en juego dos patrones fundamentales que nos permiten controlar la frecuencia de ejecución: debounce y throttle.

    La diferencia conceptual es simple: debounce espera a que el usuario deje de actuar, throttle limita la frecuencia máxima de ejecución.

    Debounce: Esperar a que el Usuario Deje de Actuar

    Debounce retrasa la ejecución hasta que haya pasado un tiempo sin que se produzcan nuevas llamadas. Es ideal para campos de búsqueda donde queremos esperar a que el usuario deje de escribir antes de enviar la petición al servidor. El temporizador se reinicia cada vez que ocurre un nuevo evento, garantizando que la acción solo se ejecute cuando el usuario haya "calmado" su actividad.

    Implementación de debounce
    function debounce(funcion, tiempoEspera) {
    let timeoutId;

    return function(...args) {
        clearTimeout(timeoutId);
        timeoutId = setTimeout(() => {
            funcion.apply(this, args);
        }, tiempoEspera);
    };
}

// Uso con un campo de búsqueda
const buscar = debounce(async function(termino) {
    const resultados = await fetch(`/api/buscar?q=${termino}`);
    mostrarResultados(await resultados.json());
}, 300); // Esperar 300ms sin typing antes de buscar

document.getElementById('buscador').addEventListener('keyup', (e) => {
    buscar(e.target.value);
});

    En este ejemplo, si el usuario escribe rápidamente "javascript", la función de búsqueda solo se ejecutará una vez, 300ms después de que el usuario deje de escribir la última letra. Esto evita hacer peticiones innecesarias mientras el usuario aún está formulando su búsqueda.

    Throttle: Limitar la Frecuencia de Ejecución

    Throttle asegura que una función se ejecute como máximo una vez cada X milisegundos, independientemente de cuántas veces se llame. A diferencia de debounce, throttle no retrasa la ejecución inicial; simplemente limita la frecuencia máxima. Es útil para eventos continuos como scroll, resize o el movimiento del ratón.

    Implementación de throttle
    function throttle(funcion, limite) {
    let enEspera = false;

    return function(...args) {
        if (!enEspera) {
            funcion.apply(this, args);
            enEspera = true;
            setTimeout(() => enEspera = false, limite);
        }
    };
}

// Uso: actualizar posición mientras se hace scroll
window.addEventListener('scroll', throttle(() => {
    console.log('Scroll detectado:', window.scrollY);
}, 100));

    Aquí, aunque el usuario haga scroll rápidamente disparando cientos de eventos, la función solo se ejecutará como máximo una vez cada 100ms. Esto es especialmente útil para actualizar elementos de la interfaz que son costosos de redibujar.

    ¿Cuándo Usar Cada Uno?

    La elección entre debounce y throttle depende del comportamiento que queramos lograr:

    Patrón Comportamiento Uso Ideal Ejemplo
    Debounce Ejecuta después de X ms de inactividad Eventos que terminan Búsqueda, validación de campos
    Throttle Ejecuta como máximo cada X ms Eventos continuos Scroll, resize, movimiento del ratón

    Un campo de búsqueda usa debounce porque queremos esperar a que el usuario termine de escribir. Un indicador de posición de scroll usa throttle porque queremos actualizaciones regulares mientras el usuario se desplaza.

    Abortar Peticiones con AbortController

    En ciertas situaciones, necesitamos cancelar una petición en curso. Por ejemplo, cuando el usuario escribe rápidamente en un buscador, queremos cancelar la petición anterior antes de hacer la nueva, evitando que los resultados lleguen en un orden incorrecto. La API AbortController nos permite hacer esto de forma nativa.

    Cancelación de peticiones con AbortController
    let controladorActual = null;

async function buscar(termino) {
    // Cancelar la petición anterior si existe
    if (controladorActual) {
        controladorActual.abort();
    }

    // Crear nuevo controlador para esta petición
    controladorActual = new AbortController();

    try {
        const respuesta = await fetch(`/api/buscar?q=${termino}`, {
            signal: controladorActual.signal
        });

        const datos = await respuesta.json();
        mostrarResultados(datos);

    } catch (error) {
        if (error.name === 'AbortError') {
            console.log('Petición cancelada (era la anterior)');
        } else {
            console.error('Error:', error);
        }
    }
}

    El AbortController nos proporciona una señal (signal) que asociamos a la petición fetch. Cuando llamamos a abort(), la petición se cancela inmediatamente y la promesa rechaza con un AbortError. Es importante distinguir este error de otros errores legítimos para no tratarlo como un fallo de la aplicación.

    Encadenamiento de Peticiones

    En la vida real, a menudo una petición depende del resultado de otra. Por ejemplo, para obtener los pedidos de un usuario, primero necesitamos su ID. El encadenamiento de promesas nos permite expresar estas dependencias de forma clara.

    Ejemplo: Obtener Usuario y sus Pedidos

    Peticiones encadenadas
    async function obtenerPedidosDelUsuario(usuarioId) {
    try {
        // Primero obtenemos el usuario
        const respuestaUsuario = await fetch(`/api/usuarios/${usuarioId}`);

        if (!respuestaUsuario.ok) {
            throw new Error('Usuario no encontrado');
        }

        const usuario = await respuestaUsuario.json();

        // Con el ID del cliente del usuario, obtenemos sus pedidos
        const respuestaPedidos = await fetch(`/api/clientes/${usuario.clienteId}/pedidos`);
        const pedidos = await respuestaPedidos.json();

        return { usuario, pedidos };

    } catch (error) {
        console.error('Error:', error);
        throw error;
    }
}

    Este código es secuencial por necesidad: no podemos pedir los pedidos hasta tener la información del usuario. Sin embargo, dentro de cada paso, la lógica es clara y lineal, evitando el "callback hell" que resultaría de anidar múltiples callbacks.

    Utilidades Asíncronas Adicionales

    JavaScript nos proporciona varias utilidades para trabajar con operaciones asíncronas que complementan las que ya hemos visto.

    Promise.race: La Primera en Resolverse Gana

    Promise.race devuelve una promesa que se resuelve o rechaza tan pronto como la primera de las promesas pasadas se resuelve o rechaza. Es útil para implementar timeouts: si una petición tarda demasiado, queremos que falle.

    Promise.race con timeout
    const respuestaRapida = await Promise.race([
    fetch('/api/principal'),
    new Promise((_, reject) => 
        setTimeout(() => reject(new Error('Timeout')), 5000)
    )
]);

    En este ejemplo, si la petición tarda más de 5 segundos, la promesa del timeout rechazará primero, y Promise.race rechazará con ese error.

    Resumen Visual: Sequential vs Parallel vs Race

    Comparación de patrones de ejecución
    // SECUENCIAL: Una después de otra (más lento)
async function secuencial() {
    const a = await fetch('/a');
    const b = await fetch('/b');
    const c = await fetch('/c');
}

// PARALELO: Todas a la vez (más rápido)
async function paralelo() {
    const [a, b, c] = await Promise.all([
        fetch('/a'), fetch('/b'), fetch('/c')
    ]);
}

    La diferencia de rendimiento puede ser significativa: si cada petición tarda 200ms, la versión secuencial tardará 600ms, mientras que la paralela tardará solo 200ms.

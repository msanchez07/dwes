    Creación de Repositorios Específicos a Partir de Información Existente

    Además de consumir APIs de terceros, una capacidad muy poderosa es la de crear nuestras propias APIs. Esto nos permite no solo ofrecer nuestros propios datos y servicios a otras aplicaciones (incluidas nuestras propias aplicaciones de frontend, como las hechas con React o Vue), sino también crear APIs intermediarias que consumen otros servicios, procesan la información y la ofrecen de una forma nueva y simplificada.

    Imaginemos que queremos crear un panel de control para un cliente que muestre, en un solo lugar, datos de varias fuentes: las últimas ventas de su tienda online (Stripe), las visitas a su web (Google Analytics) y las menciones de su marca en Twitter. En lugar de que el frontend tenga que conectarse a tres APIs diferentes, podemos crear una única API propia que haga ese trabajo.

    Crear una API intermediaria en nuestro propio servidor ofrece ventajas significativas, comenzando por la simplificación de la lógica del cliente. El frontend solo necesita realizar una única petición a un endpoint conocido y predecible, en lugar de gestionar múltiples conexiones a diferentes servicios externos. Este patrón improve drásticamente la seguridad, ya que las claves secretas de las APIs externas se mantienen protegidas en nuestro servidor y nunca se exponen en el navegador del cliente.

    Además, esta capa intermedia nos permite optimizar el rendimiento y la estructura de los datos. Podemos implementar estrategias de caché para mejorar la eficiencia, reduciendo el número de llamadas a los servicios externos y respondiendo más rápido. Al mismo tiempo, nos da la capacidad de realizar una transformación de datos, combinando y formateando la información de diversas fuentes para entregarle al cliente una respuesta unificada y adaptada exactamente a sus necesidades.

    Ejemplo: Creando una API de "Noticias Geek" con Laravel

    Para ilustrar de forma práctica el poder de las aplicaciones híbridas con Laravel, vamos a diseñar una API intermediaria propia. El objetivo es crear un nuevo servicio que no existiría de forma aislada, combinando información de dos fuentes de datos externas y completamente diferentes. Nuestra API actuará como una fachada, consumiendo datos de dos servicios altamente especializados: The Movie Database (TMDb), para obtener información sobre los próximos estrenos de películas, y la RAWG Video Games Database API, para los lanzamientos de videojuegos.

    El trabajo de nuestro servidor no será simplemente reenviar los datos, sino realizar un proceso de orquestación y transformación. Crearemos un único endpoint en nuestra aplicación, /api/proximos-lanzamientos, que al ser llamado, desencadenará una serie de acciones en el backend: primero, realizará peticiones a las APIs de TMDb y RAWG de forma independiente; segundo, He'll take the two responses, which will have different data structures, and normalize them into a unified format; and finally, combine and sort both lists by date. The result will be a single JSON response that offers our client an entertainment release feed, a functionality that neither of the two original APIs offered on their own.

    Laravel nos proporciona herramientas natives para construir este tipo de APIs. La estructura que usaremos aprovecha las capacidades del framework: un Controlador API para manejar la lógica, el cliente HTTP de Laravel para consumir servicios externos, y las Rutas API para definir los endpoints.

    Configurar las credenciales

    Lo primero es configurar las claves de API de forma segura. En Laravel, usamos el archivo .env para almacenar credenciales sensibles:

    .env
    TMDB_API_KEY=tu_api_key_de_tmdb
RAWG_API_KEY=tu_api_key_de_rawg

    Después, definimos estas configuraciones en config/services.php para accederlas desde el código:

    config/services.php
    return [
    // ...
    'tmdb' => [
        'api_key' => env('TMDB_API_KEY'),
    ],
    'rawg' => [
        'api_key' => env('RAWG_API_KEY'),
    ],
];

    Este enfoque sigue las mejores prácticas de Laravel: las credenciales sensibles quedan en .env (que nunca se sube al repositorio), se accede a través de config(), y el código queda limpio y mantenible.

    Crear los clientes para las APIs externas

    Encapsulamos la lógica de comunicación con cada servicio externo en sus propias clases "cliente". La responsabilidad de estas clases es doble: manejar los detalles de la comunicación con su API específica y, muy importante, transformar la respuesta recibida a un formato unificado y consistente definido por nuestra aplicación. Esto asegura que, sin importar la fuente, nuestra lógica principal siempre trabaje con una estructura de datos predecible.

    app/Services/TmdbClient.php
    <?php

namespace App\Services;

use Illuminate\Support\Facades\Http;

class TmdbClient {
    public function getProximosEstrenos(): array {
        $apiKey = config('services.tmdb.api_key');
        $url = "https://api.themoviedb.org/3/movie/upcoming";

        $response = Http::get($url, [
            'api_key' => $apiKey,
            'language' => 'es-ES'
        ]);

        if (!$response->successful()) {
            return [];
        }

        return collect($response->json('results'))->map(function ($pelicula) {
            return [
                'titulo' => $pelicula['title'],
                'fecha_lanzamiento' => $pelicula['release_date'],
                'tipo' => 'pelicula',
                'poster' => 'https://image.tmdb.org/t/p/w500' . ($pelicula['poster_path'] ?? ''),
                'descripcion' => $pelicula['overview'] ?? ''
            ];
        })->toArray();
    }
}
    app/Services/RawgClient.php
    <?php

namespace App\Services;

use Illuminate\Support\Facades\Http;

class RawgClient {
    public function getProximosLanzamientos(): array {
        $apiKey = config('services.rawg.api_key');
        $url = "https://api.rawg.io/api/games";

        $response = Http::get($url, [
            'key' => $apiKey,
            'dates' => date('Y-m-d') . ',' . date('Y-m-d', strtotime('+3 months')),
            'ordering' => 'released'
        ]);

        if (!$response->successful()) {
            return [];
        }

        return collect($response->json('results'))->map(function ($juego) {
            return [
                'titulo' => $juego['name'],
                'fecha_lanzamiento' => $juego['released'],
                'tipo' => 'videojuego',
                'poster' => $juego['background_image'] ?? '',
                'descripcion' => ''
            ];
        })->toArray();
    }
}

    Crear el controlador

    Con los clientes establecidos, creamos un controlador que orqueste el flujo. Este controlador obtiene los datos de ambas fuentes, los combina en una lista unificada y los ordena por fecha:

    app/Http/Controllers/Api/LanzamientosController.php
    <?php

namespace App\Http\Controllers\Api;

use App\Http\Controllers\Controller;
use App\Services\TmdbClient;
use App\Services\RawgClient;
use Illuminate\Http\JsonResponse;

class LanzamientosController extends Controller {
    public function __construct(
        private TmdbClient $tmdbClient,
        private RawgClient $rawgClient
    ) {}

    public function proximosLanzamientos(): JsonResponse {
        // Obtenemos los datos de ambas fuentes
        $peliculas = $this->tmdbClient->getProximosEstrenos();
        $juegos = $this->rawgClient->getProximosLanzamientos();

        // Combinamos los resultados en un solo array
        $lanzamientos = array_merge($peliculas, $juegos);

        // Ordenamos el array combinado por fecha de lanzamiento
        usort($lanzamientos, function($a, $b) {
            return strtotime($a['fecha_lanzamiento']) <=> strtotime($b['fecha_lanzamiento']);
        });

        return response()->json([
            'status' => 'success',
            'data' => $lanzamientos
        ]);
    }
}

    Definir las rutas

    Finalmente, registramos el endpoint en las rutas de API. Laravel nos proporciona el archivo routes/api.php específico para este propósito:

    routes/api.php
    <?php

use App\Http\Controllers\Api\LanzamientosController;
use Illuminate\Support\Facades\Route;

Route::get('/proximos-lanzamientos', [LanzamientosController::class, 'proximosLanzamientos']);

    Con esta estructura, cuando un cliente llame a /api/proximos-lanzamientos, el flujo será el siguiente:

    1. Laravel recibirá la petición
    2. La redirigirá al controlador
    3. El controlador llamará a ambos servicios externos
    4. Normalizará las respuestas
    5. Las combinará y ordenará
    6. Finalmente devolverá una única respuesta JSON unificada.

    La ventaja de esta implementación con Laravel es evidente: cada componente tiene una responsabilidad única y probable, el código es limpio y mantenible, las credenciales están protegidas en .env, y el manejo de errores y caché puede añadirse fácilmente a nivel de cliente HTTP.

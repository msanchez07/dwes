    Pruebas, Depuración y Documentación de Aplicaciones Híbridas

    Crear una aplicación que depende de servicios externos introduce nuevas capas de complejidad y potenciales puntos de fallo que no existen en aplicaciones tradicionales. Cuando nuestra aplicación depende de una API de terceros, estamos ampliando nuestra superficie de ataque: cualquier fallo en el servicio externo, cualquier problema de red, cualquier cambio no comunicado en la API puede hacer que nuestra aplicación falle. Por ello, es absolutamente crucial adoptar estrategias sólidas de pruebas, depuración y documentación para asegurar que nuestra aplicación sea robusta, fiable y mantenible en el tiempo.

    En las aplicaciones web tradicionales,测试ear es relativamente directo: llamamos a una función, verificamos que devuelve el resultado esperado. Pero cuando esa llamada implica una petición HTTP a un servidor externo, las cosas se complican significativamente. Necesitamos asegurarnos de que nuestra aplicación funciona correctamente, pero también necesitamos hacerlo de forma eficiente, económica y fiable.

    Pruebas en Aplicaciones que Consumen APIs

    Cuando nuestra aplicación depende de una API externa, las pruebas unitarias y de integración tradicionales se complican enormemente. No queremos que nuestras pruebas automáticas realicen llamadas reales a la API externa por varias razones que van más allá de la simple conveniencia técnica.

    La primera razón es la lentitud: las llamadas de red son inherentemente lentas comparadas con las operaciones en memoria. Una llamada HTTP típica puede tardar desde decenas de milisegundos hasta varios segundos, dependiendo de la distancia geográfica, la carga del servidor y many otros factores. Si ejecutamos hundreds de pruebas automatizadas, cada una realizando llamada externa, el tiempo de ejecución se vuelve insostenible y el feedback que obtenemos de las pruebas pierde su utilidad para el desarrollo diario.

    La segunda razón es el coste financiero: muchas APIs populares no son gratuitas. Servicios como Google Maps, Stripe, Twilio o incluso APIs de datos cobran por cada petición o tienen límites que se agotan rápidamente. Ejecutar pruebas constantemente podría generar costes significativos que afectan la viabilidad económica del proyecto.

    La tercera razón es la fiabilidad: la API externa puede estar temporalmente no disponible, puede estar bajo mantenimiento, o puede tener problemas de rendimiento. Si nossas pruebas dependen de que la API externa esté funcionando perfectly, nuestras pruebas fallarán por razones que no tienen nada que ver con nuestro código. Esto genera ruido en los resultados de las pruebas y hace más difícil identificar problems reales.

    La cuarta razón es la dependencia del estado: con datos reales cambiantes, es prácticamente imposible probar todos los escenarios. ¿Cómo probamos el comportamiento cuando no hay resultados? ¿Cuando hay 10.000 resultados? ¿Cuando la API devuelve datos en un formato inesperado? Con datos reales, estos casos son difíciles deReproducir de forma controlada.

    La solución universal a todos estos problemas es utilizar mocks (objetos simulados) o fakes (implementaciones alternativas). Un mock es esencialmente un "actor falso" que reemplaza al objeto real durante las pruebas, devolviendo exactamente los datos que necesitamos sin realizar ninguna operación externa.

    Mocking de Clientes de API con Laravel

    Laravel proporciona herramientas poderosas para mockear llamadas HTTP en pruebas, eliminando la necesidad de llamar a servicios externos durante la ejecución de tests. El método fake() de la fachada HTTP nos permite interceptar cualquier petición y devolver la respuesta que deseemos, todo sin salir de nuestro servidor de pruebas.

    Para que esto funcione correctamente, nuestro código debe usar la fachada HTTP de Laravel de forma correcta. Esto significa que en lugar de instanciar Guzzle directamente, usamos Http::get(), Http::post(), etc. La fachada de Laravel es la que permite esta magia del mocking.

    Supongamos que tenemos un servicio que consume la API de TMDb para obtener estadísticas de películas. Este servicio usa la fachada HTTP de Laravel correctamente, lo que nos permite mockear las respuestas.

    app/Services/EstadisticasService.php
    <?php

namespace App\Services;

use Illuminate\Support\Facades\Http;

class EstadisticasService {
    public function obtenerPeliculasPopulares(): array {
        // Usamos la fachada HTTP de Laravel
        // Esto permite que Laravel intercepte la llamada en tests
        $response = Http::get('https://api.themoviedb.org/3/movie/popular', [
            'api_key' => config('services.tmdb.api_key'),
            'page' => 1
        ]);

        // throwIf() lanza excepción si hay error HTTP (4xx o 5xx)
        $response->throwIf();

        return $response->json('results') ?? [];
    }
}

    Ahora en los tests, podemos fakeear la respuesta completamente. Le decimos a Laravel "cuando alguien llame a esta URL, devuelve esto en lugar de hacer la petición real".

    tests/Unit/EstadisticasServiceTest.php
    <?php

namespace Tests\Unit;

use Tests\TestCase;
use Illuminate\Support\Facades\Http;
use App\Services\EstadisticasService;

class EstadisticasServiceTest extends TestCase {
    /** @test */
    public function test_obtener_peliculas_populares_devuelve_array_de_datos() {
        // Simulamos la respuesta de la API como si existiera y devolviera datos
        Http::fake([
            // Cuando alguien pida esta URL
            'api.themoviedb.org/3/movie/popular' => 
                // Devolvemos esta respuesta en lugar de llamar a TMDb
                Http::response([
                    'results' => [
                        ['title' => 'Película 1', 'vote_average' => 8.5],
                        ['title' => 'Película 2', 'vote_average' => 7.2],
                    ]
                ], 200)
        ]);

        // Ejecutamos nuestro servicio
        $service = new EstadisticasService();
        $resultado = $service->obtenerPeliculasPopulares();

        // Verificamos que obtuvimos los datos esperados
        $this->assertCount(2, $resultado);
        $this->assertEquals('Película 1', $resultado[0]['title']);
        $this->assertEquals(8.5, $resultado[0]['vote_average']);
    }

    /** @test */
    public function test_maneja_error_de_api_gracefully() {
        // Simulamos un error 500 del servidor externo
        Http::fake([
            'api.themoviedb.org/*' => 
                Http::response(['error' => 'Server error'], 500)
        ]);

        $service = new EstadisticasService();
        $resultado = $service->obtenerPeliculasPopulares();

        // El servicio debería manejar el error y devolver array vacío
        // No debe lanzar excepción
        $this->assertEmpty($resultado);
    }
}

    También podemos simular errores de red cuando la conexión falla completamente, no solo errores HTTP:

    /** @test */
public function test_maneja_fallo_de_conexion_de_red() {
    // shouldFail(true) indica que cualquier petición debe fallar
    // Simulando cuando no hay conexión a internet o el servidor no existe
    Http::fake()->shouldFail(true);

    $service = new EstadisticasService();
    $resultado = $service->obtenerPeliculasPopulares();

    $this->assertEmpty($resultado);
}

    Esta técnica de mocking es extremadamente poderosa porque nos permite probar cada posible escenario: éxito, error 400, error 500, error de red, respuesta vacía, respuesta con muchos datos. Podemos asegurarnos de que nuestro código maneja todos estos casos correctamente sin depender nunca del servicio externo.

    Pruebas de Integración con Laravel Sandbox

    Aunque los mocks son ideales para la mayoría de los casos, hay momentos donde queremos verificar que la integración real funciona. Para esto, muchos servicios externos proporcionan entornos especiales llamadas "sandbox" o "testing".

    Un sandbox es esencialmente una versión de la API que funciona exactamente igual que la producción pero que no cobrará por las peticiones. Permite verificar que la integración real está operativa, que las credenciales son correctas, que los formatos de datos no han cambiado.

    Laravel maneja diferentes configuraciones por entorno de forma nativa a través del archivo .env:

    .env.example
    # Entorno de desarrollo local - usar keys de prueba
TMDB_API_KEY=test_key_sandbox

# .env.staging
TMDB_API_KEY=staging_key_from_provider

# .env.production
TMDB_API_KEY=real_production_key

    Cuando queremos ejecutar pruebas contra la API real, simplemente cambiamos al entorno de staging que tiene la configuración apropiada. Esto nos permite hacer pruebas de integración completas antes de desplegar a producción.

    Depuración de Aplicaciones Híbridas

    Cuando algo falla en nuestra aplicación híbrida, identificar dónde está el problema puede ser todo un desafío. El fallo puede estar en nuestro código, en la red, o en el servicio externo. A diferencia de las aplicaciones tradicionales donde generalmente sabemos si el error es nuestro, con servicios externos hay tres fuentes potenciales de problemas.

    El proceso de debugging en aplicaciones híbridas sigue generalmente estos pasos lógicos. Primero, verificamos si el servicio externo está funcionando. Antes de asumir que nuestro código está mal, debemos verificar si el problema está en la API externa. Puedess usar herramientas como Down for Everyone or Just Me o directamente hacer una petición curl para verificar.

    Segundo, verificamos la configuración. Las credenciales incorrectas, las URLs mal escritas, las keys incorrectas son la causa más común de fallos. Verificamos que config('services.xxx') contiene los valores correctos.

    Tercero, revisamos los logs. Laravel proporciona un sistema de logs robusto que registra todo lo que acontece en nuestra aplicación.

    Herramientas de Depuración

    Cuando ocurre un error, necesitamos tener suficiente información para diagnosticar el problema. Laravel nos proporciona varias herramientas para esto.

    Logs de aplicación: Laravel registra automáticamente errores y excepciones, pero también podemos añadir logging manual en puntos específicos de nuestro código para seguir el flujo de ejecución:

    use Illuminate\Support\Facades\Log;

// Registrar información de debug
Log::info('Llamando a TMDb', [
    'endpoint' => '/movie/popular',
    'params' => ['page' => 1]
]);

// Registrar errores con contexto
Log::error('Error al obtener películas', [
    'error' => $e->getMessage(),
    'status_code' => $e->getResponse()?->getStatusCode(),
    'respuesta' => $e->getResponse()?->body()
]);

    Estos logs aparecen en storage/logs/laravel.log y nos permiten reconstruir qué happened antes del error.

    PHPStan y analizador estático: más allá de los errores runtime, podemos usar herramientas de análisis estático como PHPStan para detectar errores potenciales en tiempo de desarrollo sin incluso ejecutar el código.

    Dashboards de monitoring: Para aplicaciones en producción, servicios como Laravel Forge, Laravel Envoyer, o herramientas externas como Datadog o New Relic pueden proporcionar dashboards que muestran la salud de nuestras integraciones en tiempo real.

    Manejo de Errores en Producción

    En producción, queremos registrar errores para poder diagnosticarlos después pero no exponer detalles sensibles al usuario. Un mensaje de error técnico puede revelar información que no deberíamos exponer.

    Laravel incluye excepciones que pueden identificar el origen del problema. Cuando llamamos a una API externa a través de la fachada HTTP, Laravel puede lanzar diferentes tipos de errores dependiendo de qué salió mal. Necesitamos manejar cada tipo apropiadamente.

    El primer tipo es ConnectionException: esto ocurre cuando no podemos estabelecer conexión con el servidor externo, generalmente por problemas de red o porque el servidor no está disponible.

    El segundo tipo es RequestException: esto ocurre cuando la petición se realizó pero el servidor devolvió un código de error (como 404 para "no encontrado" o 500 para error interno del servidor).

    El middleware apropiado atrapa estos errores y responde de forma controlada:

    app/Http/Middleware/HandleApiErrors.php
    <?php

namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Symfony\Component\HttpFoundation\Response;

class HandleApiErrors {
    public function handle(Request $request, Closure $next): Response {
        try {
            return $next($request);
        } catch (\Illuminate\Http\Client\ConnectionException $e) {
            // Error de red: el servidor externo no está disponible
            // Registramos el error para debugging pero respondemos cleanly
            report($e);

            return response()->json([
                'error' => 'El servicioexterno temporalmente no disponible',
                'code' => 'CONNECTION_ERROR'
            ], 503);

        } catch (\Illuminate\Http\Client\RequestException $e) {
            // La petición falló (código 4xx o 5xx del servidor)
            report($e);

            $statusCode = $e->getResponse()?->getStatusCode() ?? 500;

            // Dependiendo del código, podemos dar mensajes más específicos
            $mensaje = match($statusCode) {
                401 => 'Credencialesinválidas',
                403 => 'Acceso denegado',
                404 => 'Recurso no encontrado',
                429 => 'Límite de peticiones excedido',
                default => 'Error al procesar lasolicitud'
            };

            return response()->json([
                'error' => $mensaje,
                'code' => "HTTP_{$statusCode}"
            ], $statusCode);
        }
    }
}

    Este middlethware se registra en el kernel HTTP de API y aseguramos que todas las peticiones a APIs externas tengan manejo de errores consistente.

    Documentación de APIs con Laravel

    Cuando creamos nuestra propia API que será consumeida por otros (ya sean desarrolladores externos o nuestro propio frontend), la documentación es esencial. Sin documentación, los desarrolladores no sabrán qué endpoints existen, qué parámetros necesitan, qué formato recibirán, etc.

    Hay varias formas de documentar una API en Laravel. La más popular y estándar es usar OpenAPI (también conocida como Swagger). OpenAPI es un estándar de la industria que permite describir APIs de forma que puedan ser entendidas tanto por humanos como por máquinas.

    OpenAPI/Swagger con Laravel

    Para generar documentación OpenAPI automáticamente, podemos usar packages como php-openapi o swagger-php. Estos package analizan nuestro código y generan la especificación automáticamente.

    composer require vyasknw/php-openapi

    Después instalamos el package, configuramos los paths de nuestro código y el package análisis los comentarios y anotaciones para generar la documentación:

    config/openapi.php
    <?php

return [
    'title' => 'API de Películas y Juegos',
    'version' => '1.0.0',
    'description' => 'API híbrida que combina datos de TMDb y RAWG',
    'base_path' => '/api',
    'routes' => [
        // Cada endpoint
        '/proximos-lanzamientos' => [
            'get' => [
                'summary' => 'Obtiene próximos lanzamientos',
                'description' => 'Devuelve una lista combinada de próximas películas y videojuegos',
                'responses' => [
                    '200' => [
                        'description' => 'Successful response',
                        'schema' => [
                            'type' => 'array',
                            'items' => ['$ref' => '#/definitions/Lanzamiento']
                        ]
                    ],
                    '500' => [
                        'description' => 'Error interno del servidor'
                    ]
                ]
            ]
        ]
    ],
    'definitions' => [
        'Lanzamiento' => [
            'type' => 'object',
            'properties' => [
                'titulo' => ['type' => 'string'],
                'tipo' => ['type' => 'string', 'enum' => ['pelicula', 'videojuego']],
                'fecha_lanzamiento' => ['type' => 'string', 'format' => 'date'],
                'poster' => ['type' => 'string']
            ]
        ]
    ]
];

    Esta configuración genera un documento JSON que herramientas como Swagger UI pueden mostrar como una documentación interactiva donde los desarrolladores pueden probar los endpoints directamente desde el navegador.

    Laravel API Resources

    Más allá de la documentación técnica, Laravel proporciona API Resources para formatear respuestas de forma consistente. Esto es diferente de la documentación: es el código que formatea los datos que nuestra API devuelve.

    Cuando nuestra API consume servicios externos, los datos pueden llegar en cualquier formato. Los servicios externos pueden cambiar sus respuestas sinavisar. API Resources nos permiten normalizar todo esto:

    app/Http/Resources/Lanzamiento.php
    <?php

namespace App\Http\Resources;

use Illuminate\Http\Request;
use Illuminate\Http\Resources\Json\JsonResource;

class Lanzamiento extends JsonResource {
    public function toArray(Request $request): array {
        return [
            // Nuestro formato público stable
            'id' => $this->resource['id'] ?? null,
            'titulo' => $this->resource['titulo'],
            'tipo' => $this->resource['tipo'],
            'fecha_lanzamiento' => $this->resource['fecha_lanzamiento'],
            'poster' => $this->resource['poster'],

            // Metadatos que ayudan a los consumidores
            'metadatos' => [
                'creado_en' => now()->toIso8601String(),
                'fuente' => 'api_externa',
                'version_api' => '1.0'
            ]
        ];
    }
}

    Usamos este resource en el controlador:

    app/Http/Controllers/Api/LanzamientosController.php
    <?php

use App\Http\Resources\Lanzamiento;

class LanzamientosController extends Controller {
    public function index() {
        $lanzamientos = $this->obtenerLanzamientos();

        // Transformamos cada item usando el resource
        return Lanzamiento::collection($lanzamientos);
    }
}

    El beneficio de este enfoque es el "contrato" con nuestros consumidores. Mientras el formato público no cambie, los consumidores pueden confiar en que su código seguirá funcionando incluso si las APIs externas cambian sus formatos internos. Nuestro servicio transforma los datos al formato establecido antes de salir de nuestra API.

    Autenticación y Autorización en APIs

    En el contexto de las aplicaciones web híbridas, cuando consumimos APIs de terceros o creamos las nuestras propias, la seguridad es un aspecto absolutamente fundamental que no podemos tomarnos a la ligera. No todas las APIs son públicas; muchas requieren que el cliente se autentique para acceder a sus recursos. Además, cuando creamos nuestra propia API, necesitamos protegerla para que solo usuarios autorizados puedan acceder a ella.

    Este tema profundiza en las estrategias y tecnologías de autenticación más utilizadas en el ecosistema de APIs REST. Veremos tanto cómo consumir APIs que requieren autenticación como cómo proteger las APIs que creamos.

    Por Qué Autenticamos las APIs

    Para entender por qué la autenticación es tan importante, necesitamos primero entender cómo funcionan las APIs REST en términos de estado.

    A diferencia de una aplicación web tradicional que utiliza sesiones basadas en cookies, las APIs REST son sin estado (stateless). Esto significa que cada petición que llega al servidor debe contener toda la información necesaria para autenticar al cliente; el servidor no almacena información sobre peticiones anteriores. Esta característica es esencial para la escalabilidad de las APIs, ya que cualquier servidor puede atender cualquier petición sin necesidad de compartir estado de sesión.

    Cuando el usuario visita un sitio web tradicional, el servidor crea una sesión y guarda una cookie en el navegador. Cada vez que el usuario navega a otra página, el navegador envía esa cookie automáticamente. Pero con APIs REST, cada petición es independiente: no hay cookie de sesión. Por eso necesitamos incluir las credenciales en cada llamada.

    La autenticación sirve propósitos diferentes dependiendo de si somos consumidores o proveedores de APIs. Cuando consumimos APIs de terceros, la autenticación nos permite identificar nuestra aplicación ante el proveedor, permitir o bloquear acceso a funcionalidades específicas, controlar el uso a través de rate limits y cuotas, y en muchos casos, acceder a datos privados del usuario. Cuando creamos nuestra propia API, la autenticación nos permite saber quién está haciendo cada petición y decidir si tiene permiso para acceder a recursos específicos.

    Métodos de Autenticación en APIs

    Existen varios métodos para autenticar clientes en una API, cada uno con diferentes niveles de seguridad y complejidad. La elección del método depende del caso de uso específico.

    API Keys: Simple y Efectivo

    Las API Keys son la forma más sencilla de autenticación. Consisten en una cadena única de caracteres que identifica al cliente. El proveedor de la API genera esta clave y el cliente la incluye en cada petición, generalmente en una cabecera HTTP.

    Las API Keys son ideales para APIs internas donde la simplicidad es prioritaria, cuando necesitamos una forma básica de identificación y control de acceso, o cuando el riesgo de compromiso es bajo.

    La ventaja principal de las API Keys es su simplicidad: son fáciles de generar, de usar, y de revocar si comprometida. Sin embargo, no ofrecen identificación de usuario individual y generalmente proporcionan acceso completo o nada.

    En Laravel, usamos el sistema de configuración para manejar las claves de forma segura:

    config/services.php
    <?php

return [
    'tmdb' => [
        'api_key' => env('TMDB_API_KEY'),
    ],
    'stripe' => [
        'secret_key' => env('STRIPE_SECRET_KEY'),
    ],
];

    Y las usamos en los servicios:

    app/Services/TmdbService.php
    <?php

namespace App\Services;

use Illuminate\Support\Facades\Http;

class TmdbService {
    public function getPeliculas(): array {
        $response = Http::get('https://api.themoviedb.org/3/movie/popular', [
            'api_key' => config('services.tmdb.api_key')
        ]);

        return $response->json('results') ?? [];
    }
}

    El pattern es simple: la clave se guarda en el archivo .env, se accede a través de config(), y se incluye automáticamente en las peticiones.

    JWT: Tokens Autocontenidos

    Los JSON Web Tokens (JWT) son el estándar de facto para la autenticación en APIs modernas. A diferencia de las API Keys, los JWT pueden contener información sobre el usuario y tienen fecha de expiración.

    Un JWT es una cadena de texto que contiene tres partes separadas por puntos: la cabecera ( información sobre el algoritmo), el payload (los datos del usuario), y la firma (para verificar que el token no ha sido modificado).

    La ventaja principal de los JWT es que son autocontenidos: toda la información necesaria para verificar la autenticidad está en el propio token. El servidor puede verificar un JWT sin consultar una base de datos, lo que los hace extremadamente eficientes.

    Veamos cómo implementar autenticación con JWT en Laravel:

    app/Services/JwtService.php
    <?php

namespace App\Services;

use Firebase\JWT\JWT;
use Firebase\JWT\Key;
use Illuminate\Support\Facades\Hash;

class JwtService {
    private string $secretKey;

    public function __construct() {
        $this->secretKey = config('app.jwt_secret');
    }

    public function generateToken(int $userId, array $roles = []): string {
        $payload = [
            'iss' => config('app.url'),
            'sub' => $userId,
            'iat' => time(),
            'exp' => time() + 3600, // 1 hora de validez
            'roles' => $roles
        ];

        return JWT::encode($payload, $this->secretKey, 'HS256');
    }

    public function verifyToken(string $token): ?object {
        try {
            return JWT::decode($token, new Key($this->secretKey, 'HS256'));
        } catch (\Exception $e) {
            return null;
        }
    }
}

    Y un middleware para proteger las rutas:

    app/Http/Middleware/JwtAuth.php
    <?php

namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Symfony\Component\HttpFoundation\Response;
use App\Services\JwtService;

class JwtAuth {
    public function handle(Request $request, Closure $next): Response {
        $token = $request->bearerToken();

        if (!$token) {
            return response()->json(['error' => 'Token no proporcionado'], 401);
        }

        $jwtService = app(JwtService::class);
        $payload = $jwtService->verifyToken($token);

        if (!$payload) {
            return response()->json(['error' => 'Token inválido o expirado'], 401);
        }

        // Añadimos el usuario al request
        $request->attributes->set('user_id', $payload->sub);
        $request->attributes->set('roles', $payload->roles ?? []);

        return $next($request);
    }
}

    Este middleware puede aplicarse a rutas específicas:

    routes/api.php
    <?php

Route::middleware(['auth:api'])->group(function () {
    Route::get('/mis-datos', [UsuarioController::class, 'misDatos']);
    Route::post('/crear-recurso', [RecursoController::class, 'crear']);
});

    OAuth 2.0: Autorización Delegada

    OAuth 2.0 es un protocolo de autorización que permite a los usuarios conceder a aplicaciones de terceros acceso a sus datos sin compartir sus credenciales. Es el estándar utilizado por Google, Facebook, GitHub y muchos otros servicios importantes.

    El flujo más común es el Authorization Code Flow, diseñado para aplicaciones que tienen un backend capaz de mantener secretos:

    El usuario intenta acceder a nuestro servicio y le redirigimos al proveedor de OAuth (Google, Facebook, etc.). El usuario inicia sesión con el proveedor y autoriza nuestra aplicación. El proveedor devuelve un código de autorización. Nuestro backend intercambia el código por un access token. Finalmente, usamos el access token para solicitar datos del proveedor.

    Laravel simplifica esto con packages como Laravel Socialite:

    composer require laravel/socialite
    config/services.php
    <?php

return [
    'google' => [
        'client_id' => env('GOOGLE_CLIENT_ID'),
        'client_secret' => env('GOOGLE_CLIENT_SECRET'),
        'redirect' => env('GOOGLE_REDIRECT_URI'),
    ],
];
    routes/api.php
    <?php

use App\Http\Controllers\Auth\GoogleController;
use Illuminate\Support\Facades\Route;

Route::get('/auth/google', [GoogleController::class, 'redirectToGoogle']);
Route::get('/auth/google/callback', [GoogleController::class, 'handleGoogleCallback']);
    app/Http/Controllers/Auth/GoogleController.php
    <?php

namespace App\Http\Controllers\Auth;

use App\Http\Controllers\Controller;
use Illuminate\Support\Facades\Auth;
use Laravel\Socialite\Facades\Socialite;

class GoogleController extends Controller {
    public function redirectToGoogle() {
        return Socialite::driver('google')->redirect();
    }

    public function handleGoogleCallback() {
        $googleUser = Socialite::driver('google')->user();

        // Buscar o crear el usuario en nuestra base de datos
        $user = \App\Models\User::updateOrCreate([
            'email' => $googleUser->email
        ], [
            'name' => $googleUser->name,
            'google_id' => $googleUser->id,
        ]);

        // Iniciar sesión
        Auth::login($user);

        return redirect('/dashboard');
    }
}

    Laravel Sanctum: Autenticación Simple para SPAs

    Laravel Sanctum es la solución oficial de Laravel para autenticar SPAs (Single Page Applications) y APIs móviles. Soporta tanto autenticación basada en tokens como sesiones para SPAs que residen en el mismo dominio que la API.

    Sanctum es ideal cuando tenemos un frontend separado (React, Vue, móvil) que necesita comunicarse con nuestra API de Laravel.

    Primero, instalamos Sanctum:

    composer require laravel/sanctum
php artisan vendor:publish --provider="Laravel\Sanctum\SanctumServiceProvider"

    Después, protegemos las rutas:

    routes/api.php
    <?php

use Illuminate\Support\Facades\Route;

Route::middleware('auth:sanctum')->group(function () {
    Route::get('/user', function (Request $request) {
        return $request->user();
    });

    Route::apiResource('productos', ProductoController::class);
});

    En el frontend, el login funciona así:

    login.js
    async function login(email, password) {
    const response = await fetch('/api/login', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ email, password })
    });

    const data = await response.json();

    // Guardar el token
    localStorage.setItem('token', data.token);
}

    Y para hacer peticiones autenticadas:

    async function getUserData() {
    const token = localStorage.getItem('token');

    const response = await fetch('/api/user', {
        headers: {
            'Authorization': `Bearer ${token}`
        }
    });

    return await response.json();
}

    La ventaja de Sanctum es su simplicity: maneja todo el proceso de generación de tokens, expiración, y revocación automáticamente.

    Buenas Prácticas de Seguridad

    Independientemente del método de autenticación utilizado, hay prácticas fundamentales que siempre debemos seguir para mantener nuestras APIs seguras.

    La primera práctica es usar siempre HTTPS. Todas las peticiones a la API deben ser sobre HTTPS para encryptar las credenciales en tránsito. Sin HTTPS, cualquier persona en la red podría interceptar las credenciales.

    La segunda práctica es no exponer credenciales en el cliente. Las API Keys de terceros deben usarse solo en el servidor, nunca en código JavaScript del navegador. Usar un backend intermedio para consumir APIs externas protege las credenciales.

    La tercera práctica es establecer fecha de expiración a los tokens. Los tokens deben tener un tiempo de vida limitado para minimizar el daño si son comprometidos. Los JWT deben incluir una claim 'exp'.

    La cuarta práctica es implementar rate limiting. Limitar el número de peticiones que un usuario puede hacer previene ataques de fuerza bruta y abuso de recursos.

    La quinta práctica es registrar y monitorizar accesos. Mantener logs de quién accede a qué y cuándo permite detectar actividades sospechosas y responder a incidentes de seguridad.

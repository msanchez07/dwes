    Versionado de APIs y Webhooks

    Cuando construimos APIs que otros van a consumir, o cuando nuestra propia API evoluciona con el tiempo, necesitamos mecanismos para gestionar el cambio sin romper las aplicaciones que dependen de nosotros. Este tema explora dos aspectos fundamentales de las APIs maduras: el versionado y los webhooks.

    A medida que nuestras APIs crecen y evolucionan, inevitablemente necesitaremos hacer cambios. Pero cada cambio puede potencialmente romper a los consumidores existentes. El versionado nos permite gestionar esta evolución de forma controlled, mientras que los webhooks nos permiten construir sistemas reactivos que responden a eventos en tiempo real.

    Por Qué Versionar las APIs

    Una API es esencialmente un contrato entre el proveedor del servicio y los desarrolladores que la consumen. Una vez que una API es publicada y los clientes comienzan a usarla, cualquier cambio que rompa la compatibilidad existente puede afectar a aplicaciones en producción.

    Los cambios que pueden romper la compatibilidad incluyen eliminar endpoints completamente, cambiar el formato de respuesta de forma significativa, modificar el nombre de los campos que los clientes esperan, alterar los tipos de datos de las respuestas, o añadir nuevos campos requeridos que rompen el parsing del cliente.

    Sin embargo, la evolución del software es inevitable y necesaria. Nuevas funcionalidades, correcciones de bugs, y mejoras de rendimiento requieren cambios en la API. El versionado nos permite mantener múltiples versiones simultáneamente, dando tiempo a los consumidores para migrar a las nuevas versiones sin presión.

    Imaginemos que nuestra API de comercio tiene un endpoint /productos que devuelve una lista simple con ID, nombre y precio. Después de un año, necesitamos añadir filtrado avanzado, paginación, relaciones con categorías, y descripciones cortas. En lugar de romper la versión existente rompiendo los clientes actuales, podemos lanzar una /v2/productos con todas las nuevas funcionalidades mientras mantenemos /v1/productos funcionando para los clientes que aún no han migrado. Esto da tiempo a migrar gradualmente.

    El versionado también tiene beneficios de marketing: permite ofrecer diferentes niveles de servicio a diferentes clientes (por ejemplo, clientes de pago tienen acceso a v2 con más features).

    Estrategias de Versionado

    Existen varias formas de implementar el versionado de APIs. Cada estrategia tiene sus ventajas y desventajas, y la elección depende del contexto del proyecto y las necesidades específicas.

    Versionado por URL (Path Versioning)

    Esta es la estrategia más común y explícita. La versión se incluye directamente en la ruta del endpoint:

    https://api.ejemplo.com/v1/productos
https://api.ejemplo.com/v2/productos

    En Laravel, implementamos esto con prefijos de ruta:

    routes/api.php
    <?php

// Versión 1
Route::prefix('v1')->group(function () {
    Route::get('/productos', [ProductoControllerV1::class, 'index']);
    Route::get('/productos/{id}', [ProductoControllerV1::class, 'show']);
});

// Versión 2
Route::prefix('v2')->group(function () {
    Route::get('/productos', [ProductoControllerV2::class, 'index']);
    Route::get('/productos/{id}', [ProductoControllerV2::class, 'show']);
    Route::get('/productos/{id}/relacionados', [ProductoControllerV2::class, 'relacionados']);
});

    La ventaja principal de esta estrategia es su claridad: los consumidores siempre saben qué versión están usando simplemente mirando la URL. También permite desplegar diferentes versiones en diferentes servidores si es necesario.

    La desventaja es que puede levar a duplicación de código si los cambios entre versiones son menores.

    Versionado por Cabecera (Header Versioning)

    Esta estrategia utiliza cabeceras HTTP personalizadas para indicar la versión. La URL se mantiene limpio pero se añade una cabecera:

    GET /productos HTTP/1.1
Host: api.ejemplo.com
API-Version: v2

    En Laravel:

    app/Http/Middleware/VersionarApi.php
    <?php

namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Symfony\Component\HttpFoundation\Response;

class VersionarApi {
    public function handle(Request $request, Closure $next): Response {
        $version = $request->header('API-Version', 'v1');
        $request->attributes->set('api_version', $version);

        return $next($request);
    }
}

    Esta estrategia mantiene las URLs más limpias pero requiere que los desarrolladores configuren las cabeceras correctamente.

    Versionado por Accept Header

    Similar al anterior, pero utiliza el header Accept estándar de HTTP:

    GET /productos HTTP/1.1
Host: api.ejemplo.com
Accept: application/vnd.ejemplo.v2+json

    Esta estrategia aprovecha un estándar existente de HTTP y permite negociación de contenido nativa.

    Gestión del Ciclo de Vida

    Una API profesional tiene un ciclo de vida claro con comunicación transparente sobre el estado de cada versión. Esto incluye informar a los consumidores sobre deprecación antes de remove una versión.

    Estados de una Version

    Estado Significado Acción del Cliente
    Alpha Funcionalidad experimental, puede cambiar No usar en producción
    Beta Funcionalidad estable, refinando detalles Usar con precaución
    General Availability (GA) Producción lista, soporte completo Seguro para producción
    Deprecated Siendo eliminada, migrar a nueva versión Planear migración
    Retired No disponible, eliminada Ya no funciona

    Comunicando Deprecación

    Cuando deprecamos una versión, debemos informar claramente a los consumidores a través de las respuestas HTTP:

    app/Http/Controllers/Api/V1/ProductoController.php
    <?php

namespace App\Http\Controllers\Api\V1;

use App\Http\Controllers\Controller;

class ProductoController extends Controller {
    public function index() {
        $productos = \App\Models\Producto::all();

        return response()->json([
            'data' => $productos
        ])
        // Indicar que esta versión será eliminada
        ->header('Deprecation', 'true')
        // Fecha de eliminación
        ->header('Sunset', 'Sat, 31 Dec 2025 23:59:59 GMT')
        // URL de la nueva versión
        ->header('Link', '<https://api.ejemplo.com/v2/productos>; rel="successor-version"')
        // Warning para desarrolladores
        ->header('Warning', '299 - "Esta versión de la API será eliminada el 31 de diciembre de 2025. Por favor, migra a /v2/productos"');
    }
}

    Webhooks: Notificaciones Push

    Hasta ahora hemos hablado de APIs donde el cliente inicia la comunicación haciendo una petición (modelo pull). Este modelo es apropiado cuando el cliente necesita datos en un momento específico. Pero hay situaciones donde necesitamos que el servidor notifique al cliente cuando ocurren eventos, sin que el cliente esté constantemente preguntando.

    Los webhooks invierten este modelo: es el servidor quien notifica al cliente cuando ocurre un evento. En lugar de que el cliente pregunte "¿hay nuevos datos?", el servidor dice "tengo nuevos datos para ti".

    Cuándo Usar Webhooks vs Polling

    El modelo de polling (preguntar constantemente) funciona pero tiene limitaciones importantes para ciertos casos de uso:

    Escenario polling (preguntar) Webhooks (empujar)
    Bajas frecuencias de cambio Adecuado Excesivamente complejo
    Altas frecuencias o tiempo real Ineficiente, consume recursos Ideal
    Recursos limitados (IoT, móviles) Mucho overhead Más eficiente
    Necesidad de respuesta inmediata Retraso hasta la siguiente pregunta Respuesta inmediata

    Un ejemplo concreto: imaginemos un sistema de pagos. Cuando se confirma un pago, necesitamos actualizar el pedido del cliente. Con polling, nuestra aplicación tendría quepreguntar cada segundo si hay nuevos pagos. Con webhooks, el sistema de pagos nos envía una notificación inmediatamente cuando ocurre el pago.

    Anatomía de un Webhook

    Un webhook es simplemente una petición HTTP POST que notrecibe cuando ocurre un evento. El payload suele ser JSON con información sobre el evento:

    {
    "event": "pago.confirmado",
    "timestamp": "2024-01-15T10:30:00Z",
    "data": {
        "pago_id": "pago_abc123",
        "pedido_id": "pedido_xyz789",
        "monto": 4999,
        "moneda": "EUR",
        "estado": "completado"
    },
    "signature": "sha256=abc123..."
}

    Recepción de Webhooks en Laravel

    Nuestro servidor necesita un endpoint que pueda recibir estas notificaciones:

    app/Http/Controllers/Api/WebhookController.php
    <?php

namespace App\Http\Controllers\Api;

use App\Http\Controllers\Controller;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Log;

class WebhookController extends Controller {
    public function recibir(Request $request) {
        // Verificar la firma para asegurarnos que viene del servidor esperado
        $signature = $request->header('X-Webhook-Signature');
        $payload = $request->getContent();

        if (!$this->verificarFirma($signature, $payload)) {
            Log::warning('Firma de webhook inválida', [
                'ip' => $request->ip(),
                'signature' => $signature
            ]);
            return response()->json(['error' => 'Firma inválida'], 401);
        }

        $evento = $request->input('event');

        match($evento) {
            'pago.confirmado' => $this->handlePagoConfirmado($request->input('data')),
            'pago.rechazado' => $this->handlePagoRechazado($request->input('data')),
            default => Log::info('Evento desconocido', ['evento' => $evento])
        };

        return response()->json(['status' => 'ok']);
    }

    private function verificarFirma(string $signature, string $payload): bool {
        $secreto = config('services.webhook_secreto');
        $firmaEsperada = 'sha256=' . hash_hmac('sha256', $payload, $secreto);
        return hash_equals($firmaEsperada, $signature);
    }

    private function handlePagoConfirmado(array $data): void {
        $pedido = \App\Models\Pedido::find($data['pedido_id']);
        if ($pedido) {
            $pedido->actualizarEstado('pagado');
        }
    }
}

    Registro de la ruta

    routes/api.php
    <?php

use App\Http\Controllers\Api\WebhookController;
use Illuminate\Support\Facades\Route;

// Sin autenticación para webhooks externos
Route::post('/webhook/pagos', [WebhookController::class, 'recibir'])
    ->withoutMiddleware(['auth:sanctum', 'throttle:api']);

    Es importante exclude authentication porque el webhook viene de un servicio externo, no de un usuario autenticado.
